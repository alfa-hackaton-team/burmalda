# Архитектура взаимодействия ML 1 / ML 2

## 1. Два процесса

### Подготовка информации

```text
Backend/Go: источник → raw_artifact + article_version → processing_job → POST
ML 1: R02 quality PASS/FAIL → затем отдельные этапы чанков и embeddings
                                                                 ↓ готовая версия
ML 2: выделение событий → поиск похожих публикаций → события и связи с версиями
```

### Персональный анализ

```text
Backend: проверка прав → сохраненная операция + снимок контекста
ML 2: проверка входа → план поиска → ML 1 search/get_chunks
      → применимость к компании → draft + claims → проверка
      → результат для сохранения / insufficient_evidence / failed
Backend: результат + evidence + статус операции в одной транзакции
```

Follow_up использует тот же контекст, исходный insight и ограниченную снимком историю. Новые выводы принадлежат новому сообщению.

## 2. Матрица ответственности

| Компонент | Владелец | Результат | Граница |
|---|---|---|---|
| Источники/парсинг | Backend/Go; ML 1 задаёт требования к корпусу и проверяет качество | Версии, оригиналы, нормализованный текст | Один реестр и один воркер загрузки; OCR согласуется отдельно |
| Чанки/embeddings/готовность поиска | ML 1 | Восстанавливаемые ID и индекс | Не меняет текст сохранённой версии и старые evidence |
| Поиск/ранжирование/get_chunks | ML 1 | Фрагменты и ограничения | Не объявляет вывод истинным по score |
| События/объединение публикаций | ML 2 | events, event_documents | Перепечатки не считаются независимыми подтверждениями |
| Профиль/признаки | ML 2 + исходные данные backend | Версия профиля и ID признаков | Не выдумывает отсутствующие данные |
| Агент/проверка/диалог | ML 2 | Insight/сообщение с claims | Не обходит общий поиск своим загрузчиком |
| Авторизация/операции/публикация | Backend | Доступный пользователю сохраненный результат | Распределение требуется подтвердить с backend |
| Корпус оценки/рубрика | Вместе | Версионируемый набор кейсов | Один набор для сравнения улучшений |
| Шлюз LLM, бюджет, выполнение анализа, trace | ML 2 | Ограниченные вызовы и сохранённое состояние ML | Неизвестный исход не повторяется вслепую |
| Адаптеры embeddings/поиска, метрики корпуса | ML 1 | Версии индекса и диагностика | Общая конфигурация с ML 2 |
| HTTP ML, SERVICE_TOKEN, Docker ML | ML 2; ML 1 подключает свои операции | Внутренняя граница сервиса | Backend отвечает за Go, секреты и общую сборку |
| Миграции, lease/доставка, интеграционные проверки | Backend + ML 2; ML 1 для корпуса | Согласованные транзакции и восстановление | Назначить конкретных исполнителей в C04 |

Эта редакция распределяет функции прежнего ML3 между двумя ML-разработчиками и backend; отдельный третий ML-участник не предполагается. Сохранена существующая граница загрузки Go: ML 1 отвечает за качество корпуса и индекс, backend — за получение/article_versions/raw_artifacts (PostgreSQL; объектное хранилище возможно позднее). Это рабочее распределение для согласования в C04, а не утверждение о готовой инфраструктуре.

ML 1 передает данные и ограничения; ML 2 отвечает за интерпретацию. Ошибки исходного профиля исправляются у поставщика данных; ошибки преобразования профиля — в ML 2.

Нейминг входа, лимит, хеш, происхождение и lifecycle закреплены в [article-processing.md](article-processing.md). R02 проверяет точный body без исправления; пустой title не отказ. PASS разрешает продолжение полного пайплайна, не публикует готовность. R02 локально вызывается отдельно; quality-only HTTP ещё не определён. Сохранность таблиц/страниц нельзя гарантировать по одному тексту; Целевые extraction metadata и QualityResult реализованы в отдельной quality schema; старый metadata={} не поддерживается.

## 3. Целевая структура кода

Это план каталогов реализации, не перечень уже существующих модулей:

```text
ml/
  shared/        общие типы, config, error, trace
  ingestion/     проверка качества входных версий — ML 1; загрузчик находится в Go
  indexing/      чанки, embeddings и готовность версий — ML 1
  retrieval/     search, get_chunks, ранжирование — ML 1
  events/        извлечение и объединение событий — ML 2
  profiles/      преобразование исходных данных в признаки — ML 2
  agent/         план поиска, анализ, проверка, follow_up — ML 2
  adapters/      PostgreSQL/S3/модели/backend; владельцы по вызывающему компоненту
contracts/v1/ машинная схема
fixtures/v1/  синтетические сообщения
scripts/        проверка контрактов
```

Логические интерфейсы:

```text
Retriever.search(SearchRequest) → SearchResponse
Retriever.get_chunks(GetChunksRequest) → GetChunksResponse
ReadyDocuments.list(ReadyVersionsRequest) → ReadyVersionsResponse
Analyzer.analyze(AnalysisRequest) → AnalysisResponse
```

Интерфейсы не зависят от SDK конкретной модели. Для локального старта реализации работают с fixtures/in-memory адаптерами. Реальные PostgreSQL/S3/модели подключаются после согласования доступа; никакой сети не требуется для проверки текущих примеров.

## 4. Сущности и владельцы записи

| Сущность | Кто пишет | Условие |
|---|---|---|
| sources/articles/article_versions/raw_artifacts/processing_jobs | Backend/Go | Фактическое ingestion-хранение; document_id/document_version_id ML v1 сохраняют ID article/article_version |
| document_chunks, embeddings, результат quality check | ML 1 | Целевая индексация и качество; их хранение/миграции не считаются существующими. Общий статус операции Go не заменяется PASS/FAIL |
| business_profiles/business_profile_features | ML 2 | Исходные данные проверены; версия не меняется на месте |
| events/event_documents | ML 2 | Не создавать дубль при повторной обработке |
| business_contexts/request_operations/conversations | Backend | Проверка пользователя, роли, контекста |
| analysis_runs/analysis_steps | ML 2 | Запуск сохранен до платного вызова |
| insights/messages/claims/evidence/citations | Backend-слой сохранения | Атомарно с завершением request_operations |

Права БД, миграции и транзакционные границы согласуются с backend. Два компонента не должны конкурировать за одну финальную запись. DTO claim хранит отдельно назначение, тип знания и результат проверки; их сохранение описано в api-compatibility.md. DTO claim не содержит владельца: слой сохранения устанавливает insight_id либо message_id, а также технические ID evidence и timestamps.

## 5. Качество корпуса

1. Сохранять оригинал и метаданные до объявления готовности.
2. Go и контрольные примеры проверяют извлечение; ML1 проверяет доступный body/метаданные. Потерянную таблицу или сноску по одному тексту не считать гарантированно обнаруженной.
3. Различать published_at и retrieved_at; неизвестную дату не подменять.
4. Go сравнивает content_hash и parser_version с последней article_version: A → B → A сохраняется как три версии. ML не пересчитывает content_hash только от текста.
5. Создавать чанки для новой версии; не менять текст под прежним chunk_id.
6. Использовать одну embedding-модель/размерность в индексе. Переиндексация не удаляет цитируемые старые чанки.
7. После ошибки исходника не выдавать старый текст как свежий без предупреждения.

Начальные ориентиры чанков из схемы — 300–600 токенов, перекрытие 50–100; качество проверяется на реальных вопросах. Числа, единицы, периоды и условия должны попадать в доступный контекст вместе.

## 6. Качество событий и выводов

ML 2 различает новое событие, дополнительное подтверждение, изменение стадии и опровержение. Совпадение темы/заголовка недостаточно для объединения. Проверяются участники, действие, территория, период и стадия.

У событий есть статусы candidate/confirmed/disputed/rejected. В первом автоматическом happy path анализируются confirmed; disputed требует явного условного ответа, rejected не публикуется как актуальный факт. Candidate не становится confirmed по одному similarity score.

Агент последовательно ищет: факт → даты → применимость → контекст → исключения/противоречия → позицию банка при необходимости. Останавливается при достаточных основаниях, отсутствии нужных данных либо исчерпании бюджета.

Два отдельных вопроса проверки: «источник подтверждает событие?» и «это последствие обосновано для данной компании?». Наличие кредита не доказывает плавающую ставку; изменение новых договоров не доказывает изменение платежей по старым.

Все существенные утверждения summary, consequences, recommended_actions и bank_view должны быть представлены в claims. Иначе формальная проверка списка claims может пропустить недоказанный текст в других полях. Схема JSON не проверяет смысловое покрытие; это обязанность проверки ML 2 и общей ручной оценки.

## 7. Версии и воспроизводимость

Фиксировать версии профиля, документов, конфигурации поиска, модели, промпта и обработки. Снимок события хранить в request_snapshot: events пока не имеет версий.

v1 поиска работает по текущему корпусу; поля corpus_snapshot_id в машинной схеме нет. Сохраненные ответы инструментов позволяют проверить, что видел агент, но не гарантируют повторение того же поиска позднее. Хранилище полных артефактов и его срок жизни нужно согласовать; analysis_steps хранит только сокращенную трассировку.

Фоновая обработка требует журнала готовности и учета обработанных версий — таких таблиц нет в текущей БД. До согласования фоновой доставки использовать фиксированный локальный корпус/ручную передачу, не обещая надежность непрерывной обработки.
