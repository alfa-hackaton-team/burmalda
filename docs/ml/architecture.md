# Архитектура ML

```text
Go: загрузка → raw_artifact + article_version + source snapshot → processing_job
ML1: R02 quality → chunking → embeddings → индекс → search/get_chunks
ML2: профиль + события → поиск → claims/evidence → проверка → результат
Go: транзакционное сохранение → публичный ответ
```

## Ответственность

| Владелец | Область |
|---|---|
| Go/backend | Источники, загрузка/парсинг, оригиналы и версии, исходные CSV, права, доставка и публикация |
| ML1 | Canonical документ, качество корпуса, чанки, embeddings, индекс, retrieval и исторические фрагменты |
| ML2 | Профиль/признаки, события, агент, claims/verification, follow_up, HTTP ML, LLM-бюджеты и trace |

В этой ветке ML1 реализованы R01 fixtures и R02 quality. Остальная цепочка — план, не работающий сервис. Реальные таблицы определяют миграции Go; [SQL RFC](../rfc/database_scheme.md) описывает целевое ML-хранение.

## Обязательные границы

- Один сохранённый документ: ID и body Go сохраняются в ML без переписывания. Исторические чанки не подменяются новой версией.
- Quality PASS — прохождение правил текста, не истинность, готовность индекса или SUCCEEDED общей операции.
- Retrieval score — оценка поиска, не confidence вывода. Empty отличается от технической ошибки.
- Доступ проверяет доверенный адаптер; null business_context_id не отключает права.
- Выводы ссылаются на разрешённые чанки/признаки. Позиция банка требует банковского источника.
- Follow_up использует переданный исходный снимок и историю; исходный insight не изменяется.
- Результат ML публикуется backend после сохранения; повтор не создаёт второй результат или платный запуск.
