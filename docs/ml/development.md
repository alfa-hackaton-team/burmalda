# План разработки и приемки

## 1. Порядок работ

Не нужно ждать завершения всей инфраструктуры. Сначала обе части работают на фиксированных примерах; затем подключаются корпус, модель и сохранение. Пункты с backend не считаются реализованными только потому, что согласованы внутри ML.

### Этап 0. Общая основа — вместе

| ID | Задача | Результат | Готово, когда |
|---|---|---|---|
| C01 | Прочитать contracts.md и выбрать по одному запросу/ответу | Одинаковое понимание полей | Обе стороны умеют собрать и разобрать fixtures |
| C02 | Зафиксировать рабочую конфигурацию | Названия/версии моделей, размерность, бюджеты | Для локального режима допускается заглушка; для реальной индексации N уже выбран |
| C03 | Определить первый реальный сценарий | Компания, роль, событие, источники | Есть пример профиля и документы с происхождением |
| C04 | Согласовать интерфейс с backend | Владельцы, снимок, транзакции, отображение API | Проверена api-compatibility.md; назначены ответственные за бывшие задачи ML3 и миграции полей claims |

| ID | Задача | Зависимость | Приемка |
|---|---|---|---|

### Этап 2. Первая интеграция

| ID | Задача | Приемка |
|---|---|---|
| I01 | Заменить заглушку реальным search/get_chunks | Форматы не требуют ручной правки |
| I02 | Пройти один сценарий целиком | Insight имеет проверяемые ID, цитаты и признаки профиля |
| I03 | Повторить с отсутствующим признаком | Получено уточнение/нехватка данных, а не уверенный эффект |
| I04 | Пройти уточнение и обновление документа | Исходные claims сохранены, исторические evidence доступны; trace нового запуска отличается и связан через parent_trace_id |
| I05 | Подключить сохранение backend | Один результат и статус в одной транзакции; knowledge_type, verification_status, assumptions и time_horizon не теряются при записи/чтении и преобразовании в публичный API |
| I06 | Проверить параллельные повторы и сбой доставки | Нет второго платного запуска; результат доставляется повторно без регенерации |

### Этап 3. Фоновый процесс и качество

1. Согласовать и реализовать журнал готовности, учет обработанных версий и восстановление курсора.
2. Подключить получение новых документов и выделение/обновление событий.
3. Измерять свежесть источников отдельно от возраста найденного документа.
4. Расширять общий набор новыми темами и реальными ошибками.
5. Добавлять гибридный поиск/reranker/дополнительные инструменты по измеренным улучшениям.
6. Автоматическую ленту, уведомления, массовый повторный анализ и группы компаний включать после отдельного продуктового решения.

## 2. Общие проверочные сценарии

| Кейс | Ожидаемое поведение |
|---|---|
| Подтвержденное событие и применимый профиль | Полезный вывод с валидными evidence |
| Документы не найдены | empty не превращается в утверждение об отсутствии события в мире |
| Поиск недоступен | Техническая ошибка явно отличается от недостатка оснований |
| Есть часть источников | partial с объяснением; вывод не сильнее доступных данных |
| Неизвестны условия кредита | Нет вывода о конкретном платеже |
| Изменение только для новых договоров | Действующие договоры автоматически не затрагиваются |
| Десять перепечаток | Один исходный канал подтверждения, не десять независимых |
| Источник исправлен | Новая версия, старая цитата доступна, затронутый вывод помечен для пересмотра |
| Даты публикации и действия разные | Пользователь понимает, когда изменение применяется |
| Другой регион/продукт | Нет ложного персонального вывода |
| Противоречие | Условный ответ или недостаток оснований, противоречие не скрыто |
| Нет позиции банка | bank_view=null |
| Уточнение содержит новый вывод | Новые claims/evidence, исходный insight не переписан |
| Два одинаковых запроса | Один запуск и один сохраненный результат |
| Чужой контекст/ID | Нет утечки и нет доступа по одному знанию UUID |
| Инструкция внутри источника | Она остается цитируемыми данными, не командой агенту |

Для кейса хранить вопрос, снимок профиля/события, документы, ожидаемые и запрещенные выводы, объяснение оценки. JSON fixtures покрывают формы сообщений, а таблица выше — будущую функциональную/смысловую проверку. Сервисные и смысловые кейсы ещё не реализованы. Скрипт test_ml_contracts.py проверяет регрессии контрактов: снимок исходного разбора, чужие ссылки, границы истории, пары запрос/ответ, trace и независимость типов claims.

## 3. Метрики и пороги

- ML 1: покрытие корпуса, успешность парсинга, задержка индексации, Recall@10 по документам, доля полезного в первых результатах, p50/p95 поиска.
- ML 2: смысловая поддержка claims, корректность применимости, полезность действий, точность воздержания и частота ошибочных отказов.
- Вместе: доля успешных сценариев, сохранность evidence, повторные запуски, время/стоимость анализа.

Нужно 100% валидных ссылок и support у опубликованных claims — это инвариант схемы. Порог Recall и допустимую задержку принять после baseline. Не путать формальную валидность evidence с истинностью вывода. Качество не улучшается простым отказом на всех вопросах.

## 4. Вопросы, которые не блокируют локальный старт

| Вопрос | Что делаем сейчас | До чего обязательно решить |
|---|---|---|
| Провайдер моделей | Fixture-адаптеры | До реальных платных вызовов |
| Embedding-модель и N | Контракт результата без векторов | До миграции vector(N) и реальной индексации |
| Источники и доступность | Синтетический/сохраненный корпус | До фоновой загрузки и обещаний покрытия |
| HTTP или локальные вызовы | Локальные логические методы | До разделения сервисов |
| Снимки корпуса | Сохраняем fixture/выдачу, не обещаем точный replay | До требования полной воспроизводимости |
| Журнал готовности | Ручной фиксированный набор версий | До надежной фоновой обработки |
| Семантика embedded/analyzed | In-memory поиск готовых данных | До чтения реальной БД |
| Надежная доставка результата | Fixture сохранения | До production и параллельных операций |
| Денежный лимит | Платный режим выключен | До подключения платной модели |

## 5. Definition of Done интеграции

1. Проверка fixtures, регрессионные тесты и полная JSON Schema проходят; обе реализации используют одни сообщения.
2. Реальный поиск возвращает корректные версии и исторические чанки.
3. Результат объясняет событие, применимость, условия и следующий шаг; все утверждения покрыты claims.
4. Нехватка данных и технический сбой различаются.
5. Follow_up использует корректную историю и не изменяет исходный insight.
6. Повтор операции не вызывает повторную оплату; сбой сохранения имеет проверенный путь восстановления.
7. Результат связан с теми же operation/context/event, что и запрос.
8. Есть общий отчет по кейсам, ограничениям, задержке и стоимости.

Пункты 2–8 еще предстоит реализовать и проверить. Текущие артефакты закрывают подготовку интерфейсов и независимый старт.

## 6. Согласование и ежедневная работа

На первой встрече пройти один analysis.request → search.request → search.ok → analysis.ok и один insufficient_evidence. Подтвердить владельцев, первый реальный сценарий и дату I01. Отдельно передать backend раздел о сохранении и идемпотентности.

На контрольной точке ML 1 сообщает покрытие/готовность корпуса, изменения формата и ошибки retrieval. ML 2 сообщает необходимые поисковые задачи, пропущенные основания, неверные выводы и бюджеты. Для ошибки нужны ID кейса, trace, конфигурация, ожидаемый/фактический результат и владелец.

Изменять контракт до реализации обеих сторон, одновременно обновляя схему, fixtures и документацию. После фиксации v1 несовместимые изменения идут через v2/миграцию; не добавлять скрытые обязательные поля. При споре о качестве сохранять воспроизводимый кейс, а не только скриншот ответа.
