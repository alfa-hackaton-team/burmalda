# ML 1 + ML 2: комплект для начала разработки

Редакция 1.1 от 24 октября 2026 года. Статус: рабочая спецификация для разработки и согласования командой; не описание уже реализованного сервиса.

ML 1 — корпус документов, их качество, индексация и поиск. ML 2 — события, бизнес-профиль, агент, проверка выводов и уточнения. Цель: получить персональный вывод из события и профиля компании с восстанавливаемыми основаниями.

## Как читать и согласовывать

Начинать с этого README, затем пройти архитектуру, контракты, совместимость API и план разработки. Для автономной проверки fixtures достаточно этой папки. Для интеграции нужны актуальные API и схема БД из репозитория; reference содержит только исторические снимки. Для открытых решений используйте разделы 4 и 6 плана разработки.

```text
ml/
  README.md             точка входа и рабочие решения
  architecture.md       процессы, модули и ответственность
  contracts.md          описание интерфейсов и инвариантов
  development.md        задачи, зависимости и приемка
  api-compatibility.md  границы API, преобразование DTO и хранение
  ml1/                  подробное ТЗ и локальный AGENTS.md для ML 1
  contracts/v1/         JSON Schema и инструкция
  fixtures/v1/          16 примеров и manifest.json
  scripts/              проверка примеров без зависимостей
  reference/            снимки схемы БД и подробного RFC
```

## Что читать

1. [Архитектура и ответственность](architecture.md): процессы, структура модулей, данные и границы.
2. [Контракты](contracts.md): методы, обязательность полей, ошибки и правила сохранения.
3. [План разработки](development.md): задачи, зависимости, приемка и первая интеграция.
4. [JSON Schema](contracts/v1/contracts.schema.json): точные формы сообщений; нужный тип выбирается из `$defs`.
5. [Примеры](fixtures/v1/manifest.json): 16 синтетических запросов и ответов.
Локальная папка `ml1/` содержит ТЗ и контекст агента для ML 1; эти материалы не входят в репозиторий. Инструкция подключения R01 для команды — в [ml/README.md](../../ml/README.md).

Актуальные требования хранения — в [целевой схеме БД](../rfc/database_scheme.md). Файлы reference — исторические снимки, их не редактируют вслед за рабочей схемой. Разделение логического ML v1, публичного API v0.1 и отображение полей описаны в [совместимости API](api-compatibility.md). Новые поля claims требуют миграции до интеграции; наличие документа не означает, что миграция выполнена.

## Начать сейчас

Из папки `docs/ml` (или из скопированной папки `ml`):

```bash
python3 scripts/check_ml_contracts.py
```

Проверка работает без внешних библиотек и сети. Она проверяет используемое подмножество JSON Schema, пары запрос/ответ, снимок исходного разбора, границу истории, уникальность запусков, ID и точные цитаты. Это не полноценный валидатор Draft 2020-12 и не проверка смысловой достоверности. Для проверки полной схемы предусмотрен режим `--full`; установка и регрессионные тесты описаны в [инструкции](contracts/v1/README.md). Для production-адаптеров также нужны прикладные проверки и проверка прав по хранилищу.

ML 1 начинает с `SearchRequest/SearchResponse` и fixtures `search.*`, затем `GetChunks*`. ML 2 начинает с `AnalysisRequest/AnalysisResponse`, используя `search.ok.json` и `chunks.ok.json` как ответы заглушки. Оба используют один синтетический профиль и событие из `analysis.request.json`.

В `ml_runtime/` находится локальный Python-каркас ML2: валидация AnalysisRequest/Response, адаптер Retriever, ограниченный поиск, evidence-bound drafting и проверка ссылок. `AnalysisService` проводит запрос через Retriever и model client; для follow_up использует исходный снимок evidence. Model client соблюдает оставшийся deadline анализа, использует OpenAI-совместимый gateway организаторов и разрешает только точные model ID из приложения 3. По умолчанию выбрана `z-ai/glm-5.3-flash`. Ключ берётся только из `ML_LLM_API_KEY`. Выполнен один платный smoke-прогон на синтетическом fixture: gateway вернул корректный JSON, агент ответил `insufficient_evidence` с объяснением недостающих данных; это не проверяет качество успешного insight.

Для R02 `ArticleProcessingCoordinator` сначала запускает quality gate ML1 и только при PASS продолжает индексацию и обработку событий ML2. Входная проверка принимает обязательные поля extraction metadata из целевого контракта; адаптер `ML1R02QualityGate` использует canonical document и правила ML1. Этот путь зависит от ML1 PR с R02. HTTP API и production-персистентность операций пока не реализованы; in-memory store служит только локальной разработке. Независимая смысловая проверка claims также остаётся незакрытой.

Для одного платного smoke-прогона синтетического fixture из корня репозитория нужен Python 3.10+. Пример для macOS/Linux с Python 3.12:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r ml_runtime/requirements.txt
# ML_LLM_API_KEY должен быть безопасно задан в окружении этого shell.
export ML_LLM_BASE_URL='https://changellenge.up.railway.app/v1'
export ML_LLM_MODEL='z-ai/glm-5.3-flash'
.venv/bin/python -m ml_runtime.run_agent_fixture
```

Не коммитьте и не публикуйте ключ. Runtime читает его только из переменной процесса. Для запасного gateway вручную задайте его Base URL в `ML_LLM_BASE_URL`; автоматического переключения нет.

Изменения относительно PR №6: [review-changes.md](review-changes.md).

## Рабочие решения этой редакции

| Вопрос | Стартовое решение |
|---|---|
| Организация | Общий Python ML-проект; логические вызовы через интерфейсы, без обязательного отдельного HTTP-сервиса поиска |
| Первый сценарий | Одна компания, роль CFO, заранее выбранное событие, один insight и follow_up |
| События | ML 2; до фонового pipeline событие задается fixture/вручную |
| Профиль | ML 2 отвечает за преобразование; исходные данные и права дает backend; первый профиль фиксирован |
| Поиск | Embeddings + явные фильтры; полнотекстовый поиск и reranker добавляются по оценке |
| Готовность | Рабочая цель — `embedded` или `analyzed`; требуется согласовать отличие от SQL-примера исходного RFC |
| Evidence | В v1 только `document_chunk` и `profile_feature`; таблицы event_facts отложены |
| История | Известные ID читаются адресно; точное повторение живого поиска не обещается |
| Уточнение | Backend передаёт снимок исходного insight с claims/evidence, историческими чанками и структурированной историей |
| Трассировка | Разные запуски имеют разные trace_id; follow_up ссылается на исходный через parent_trace_id |
| Совместимость | claim_type — назначение, knowledge_type — тип знания; публичный AgentResponse строит адаптер |
| Сохранение | ML готовит результат; backend транзакционно сохраняет публичный результат и статус операции |
| Оценки | Неизвестные nullable-оценки — null, similarity не становится confidence |
| Модели | Провайдеры подключаются адаптерами; до выбора embedding-модели не создавать миграцию vector(N) |

Это принятые для проекта документа рабочие значения, а не подтверждение согласия отсутствующих участников. Они позволяют начать локальную разработку; внешние зависимости описаны в плане. Новые поля DTO не становятся колонками БД автоматически.
