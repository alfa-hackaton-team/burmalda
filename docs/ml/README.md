# ML 1 + ML 2: комплект для начала разработки

Редакция 1.0 от 24 октября 2026 года. Статус: рабочая спецификация для разработки и согласования командой; не описание уже реализованного сервиса.

ML 1 — корпус документов, их качество, индексация и поиск. ML 2 — события, бизнес-профиль, агент, проверка выводов и уточнения. Цель: получить персональный вывод из события и профиля компании с восстанавливаемыми основаниями.

## Как отправить на согласование

Скопируйте или отправьте целиком эту папку `ml`. Все документы, исходные материалы, контракты, примеры и проверочный скрипт находятся внутри; доступ к остальному репозиторию не нужен. Начинать чтение с этого README, затем пройти архитектуру, контракты и план разработки. Для обсуждения открытых решений используйте разделы 4 и 6 плана разработки.

```text
ml/
  README.md             точка входа и рабочие решения
  architecture.md       процессы, модули и ответственность
  contracts.md          описание интерфейсов и инвариантов
  development.md        задачи, зависимости и приемка
  contracts/v1/         JSON Schema и инструкция
  fixtures/v1/          16 примеров и manifest.json
  scripts/              проверка примеров без зависимостей
  reference/            снимки схемы БД и подробного RFC
```

## Что читать

1. [Архитектура и ответственность](architecture.md): процессы, структура модулей, данные и границы.
2. [Контракты](contracts.md): методы, обязательность полей, ошибки и правила сохранения.
3. [План разработки](development.md): задачи, зависимости, приемка и первая интеграция.
4. [JSON Schema](contracts/v1/contracts.schema.json): точные формы сообщений; нужный тип выбирается из `$defs`.
5. [Примеры](fixtures/v1/manifest.json): 16 синтетических запросов и ответов.

Требования хранения взяты из [схемы БД](reference/database_scheme.md). [Ранее подготовленный RFC](reference/ml_work_plan_and_contracts.md) сохраняется как подробное обоснование и список альтернатив. Файлы в reference — снимки материалов на момент подготовки комплекта, а не отдельные источники для редактирования схемы проекта. При различиях контрактов использовать этот комплект и его JSON Schema; изменения самой схемы БД требуют отдельного согласования.

## Начать сейчас

Из папки `docs/ml` (или из скопированной папки `ml`):

```bash
python3 scripts/check_ml_contracts.py
```

Проверка работает без внешних библиотек и сети. Она проверяет используемое подмножество JSON Schema, согласованность примеров, ID и точные цитаты. Это не полноценный валидатор Draft 2020-12 и не проверка смысловой достоверности. Для production-адаптеров нужен полноценный валидатор и прикладные проверки из contracts.md.

ML 1 начинает с `SearchRequest/SearchResponse` и fixtures `search.*`, затем `GetChunks*`. ML 2 начинает с `AnalysisRequest/AnalysisResponse`, используя `search.ok.json` и `chunks.ok.json` как ответы заглушки. Оба используют один синтетический профиль и событие из `analysis.request.json`.

Сейчас созданы документация, схемы, примеры и проверочный скрипт. Парсеры, индекс, модельный агент, API, миграции и backend-адаптеры еще не реализованы. Команда выше проверяет контракты, но не запускает сервис.

## Рабочие решения этой редакции

| Вопрос | Стартовое решение |
|---|---|
| Организация | Общий Python ML-проект; логические вызовы через интерфейсы, без обязательного отдельного HTTP-сервиса поиска |
| Первый сценарий | Одна компания, роль CFO, заранее выбранное событие, один insight и follow_up |
| События | ML 2; до фонового pipeline событие задается fixture/вручную |
| Профиль | ML 2 отвечает за преобразование; исходные данные и права дает backend; первый профиль фиксирован |
| Поиск | Embeddings + явные фильтры; полнотекстовый поиск и reranker добавляются по оценке |
| Готовность | Рабочая цель — `embedded` или `analyzed`; требуется согласовать отличие от SQL-примера исходного RFC |
| Evidence | В v1 только `document_chunk` и `profile_feature`; таблицы event_facts отложены |
| История | Известные ID читаются адресно; точное повторение живого поиска не обещается |
| Сохранение | ML готовит результат; backend транзакционно сохраняет публичный результат и статус операции |
| Оценки | Неизвестные nullable-оценки — null, similarity не становится confidence |
| Модели | Провайдеры подключаются адаптерами; до выбора embedding-модели не создавать миграцию vector(N) |

Это принятые для проекта документа рабочие значения, а не подтверждение согласия отсутствующих участников. Они позволяют начать локальную разработку; внешние зависимости описаны в плане. Новые поля DTO не становятся колонками БД автоматически.
