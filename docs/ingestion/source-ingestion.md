# Загрузка материалов из источников

Загрузка источников создаёт воспроизводимую базу материалов для поиска и анализа. Система получает публикации через поддерживаемые способы доставки, сохраняет оригиналы, приводит данные к единому виду и передаёт их обработке событий. Для обычных новостей используется опрос примерно раз в 15 минут; точный Интервал задаётся для каждого источника.

## Цепочка обработки и ответственность

Реестр источников → планировщик → адаптер → оригинал (`RawArticle`) → нормализация → унифицированная публикация (`NormalizedArticle`) → техническая дедупликация → сохранённые материалы → чанки и индекс ML1 → обработка событий ML2.

Go-бэкенд владеет реестром, административным API, планировщиком и воркером загрузки. Планировщик определяет время запуска, воркер выполняет получение, сохранение оригинала, нормализацию, техническую дедупликацию, повторы и учёт состояния задач. Воркер может быть отдельным процессом того же Go-приложения.

ML1 отвечает за качество текста, чанки, embeddings и поиск. ML2 извлекает и объединяет события из готовых версий документов. Go передаёт `NormalizedArticle` и безопасное описание источника через `POST /internal/v0.1/article-processings`, а состояние получает по идентификатору операции. Этот маршрут координирует оба этапа; `SUCCEEDED` означает готовность поиска и сохранённый результат событий. Идемпотентный ключ связан с версией материала и конфигурацией обработки. В ML не передаются конфигурация доступа к издателю и секреты. Управление реестром и синхронизацией остаётся только в Go.

Порядок предпочтения — официальный API или канал издателя → RSS → Atom → другой официальный структурированный канал → допустимый разбор HTML как запасной вариант. Общий RSS-адаптер обслуживает несколько конфигураций. Поддержка любого URL не обещается; неподдерживаемый адаптер требует реализации и проверки.

## Граница с ML1 R02

Единый словарь — [article-processing.md](../ml/article-processing.md). Физически Go хранит articles/article_versions/raw_artifacts и создаёт processing_jobs; document_id/document_version_id ML v1 сохраняют article_id/article_version_id. Сохранение предшествует POST; raw_ref в обычном RSS может вести на снимок ленты. ML1 проверяет точный сохранённый body без нового parsing/normalization. Максимум body — 131072 UTF-8 байта без заголовка, без обрезания; пустой title допустим, дата публикации может отсутствовать. content_hash использует сериализацию Go заголовка/текста/даты, не только body.

Quality PASS/FAIL отделены от состояния всей операции; полный SUCCEEDED требует готовности результатов/поиска. Целевой вход R02 уже определяет обязательные extraction_method/extraction_errors и закрытые коды по [quality schema](../ml/contracts/quality/v1/quality.schema.json); backend должен передавать их. Прежний metadata={} не принимается. Полнота извлечения по-прежнему не гарантирована. Отдельно подготовленные банковские PDF/CSV пока не подключены этим маршрутом. Постановка существующих версий в ML после включения пайплайна требует отдельной доработки Go: обычный опрос неизменившейся статьи не создаёт job.

## Состав реестра источников

Запись источника включает `source_id`, `name`, `source_role` (`external`/`bank`/`expert`), `source_type`, `trust_level`, `adapter_type`, адрес и конфигурацию, `enabled`, `polling_interval_seconds`, `last_sync_at`, `last_success_at`, необязательный курсор, `health`, очищенный `last_error` и `config_version`. Эти поля разделяют назначение источника, доверие к нему и техническое состояние.

Уровень доверия — документированный класс, а не выдуманный численный рейтинг. Конфигурация проверяется по возможностям адаптера. Учётные данные передаются ссылкой на секрет; его значение не возвращается в API и не хранится в редактируемой конфигурации.

Нужно различать внутренние материалы Альфы, доверенные внешние источники и другие проверенные классы. Доверие к источнику и релевантность материала — разные свойства; источник банка не делает прогноз бессрочно актуальным. Добавление источника само по себе не присваивает ему доверенный статус.

Для выбранных RSS/Atom-источников опция `article_html=true` загружает материалы по ссылкам и принимает HTML либо текстовый PDF. Название опции сохраняется для совместимости с существующими конфигурациями. PDF без извлекаемого текста требует отдельного OCR-процесса и пока фиксируется как ошибка записи.
Для HTML-страниц по умолчанию используется `<article>` или `<main>`. Если издатель использует другую разметку, у источника задаются `article_container_id` и при необходимости `article_exclude_classes`; отсутствие настроенного контейнера фиксируется как ошибка конкретной записи. Правила извлечения зависят от конфигурации источника, а не от домена в коде.

## Оригиналы, нормализация и версии

Оригинал нужен для восстановления и повторного разбора, нормализованный текст — для одинаковой обработки разных источников, версия — для точной ссылки из вывода. Эти три задачи не следует объединять в одну изменяемую запись: иначе обновление статьи сделает старую цитату непроверяемой.

Оригиналы сохраняются для повторной обработки без внешней загрузки. Происхождение включает `source_id`, `fetched_at`, курсор запроса, контрольную сумму, тип содержимого и ссылку на хранилище. Слой хранения может использовать закрытое объектное хранилище или постоянные тома демонстрационного окружения; независимо от технологии сохраняются целостность и адресуемая версия.

Go извлекает основной текст из HTML/PDF до отправки в ML. `NormalizedArticle` содержит идентификаторы публикации и версии, `source_id`, `external_id` и `canonical_url` при наличии, заголовок (может быть пустым), непустой текст, дату публикации при наличии, время загрузки, язык и автора при наличии, метаданные и `raw_ref` сохранённого оригинала. ML не скачивает оригинал по `raw_ref`; анализ изображений или исходной разметки PDF согласуется отдельно. Дата публикации не заменяется временем загрузки незаметно. Материал Альфы может быть аналитическим PDF, а не новостной публикацией: общая модель документов и доказательств сохраняет этот тип. Текст сверх согласованного с ML1 лимита отклоняется явно, без незаметного обрезания.

Для технической идентификации используются источник и внешний ID, канонический URL, а при их отсутствии — устойчивый отпечаток. Запасной метод и версионирование конфигурации нормализации согласуются после исследования материалов. Изменение текста известной публикации создаёт версию содержимого, а не новое независимое событие. Идентичный материал не должен повторно расходовать средства на векторизацию и извлечение фактов; смысловые дубли между издателями обрабатывает ML2 отдельно.

Этапы имеют ключ идемпотентности и сохранённый результат; два пересекающихся опроса не публикуют дубли. Планировщик учитывает уже выполняемые задачи, а обновление курсора связано с сохранением соответствующей порции данных. Курсор нельзя продвигать до подтверждённой записи: при сбое это привело бы к потере материала. Сверка восстанавливает обработку с последней согласованной точки.

## Опрос, ошибки и состояние

Интервал задаётся для каждого источника; опрос новостей не применяется к клиентским наборам данных. В следующих версиях: уведомления от источника (webhook). Обязательного брокера сообщений нет.

Состояние источника принимает значения `UNKNOWN`, `HEALTHY`, `DEGRADED`, `UNAVAILABLE`; признак включения `enabled` хранится отдельно. Отключение останавливает новые автоматические синхронизации и не удаляет накопленные материалы. Ручной запуск проходит проверку прав и правил управления источником; интерфейс не должен показывать успешный запуск операции, которую сервер не разрешил.

Повторы ограничены и увеличивают интервал с учётом лимитов провайдера. Параллельность и число попыток соотносятся с нагрузкой источника и доступным бюджетом. Постоянная ошибка конфигурации не повторяется как временная недоступность. Ограничения частоты, загрузка, разбор, сохранение и последующая обработка учитываются раздельно; успешное получение файла не означает готовый поисковый индекс.

Сбой адаптера изолирован по источнику; сохранённые новости не удаляются. Внутри ленты ошибки отдельных ссылок записываются по каждой записи: удачные статьи сохраняются, опрос получает `PARTIAL`, источник — `DEGRADED`. Если все ссылки не обработаны, опрос получает `FAILED`. Статьи с URL и временной ошибкой получают отдельное задание в PostgreSQL с числом попыток, временем следующего запуска и lease. Повторы идут с возрастающей задержкой, разбросом и учётом `Retry-After`; после лимита попыток задание переходит в `DEAD`. Постоянные ошибки переходят в `DEAD` сразу. После частичного или полного опроса HTTP-валидаторы не продвигаются, чтобы не пропустить неудачные записи при следующем опросе ленты. Повтор с теми же входными данными возвращает тот же идентификатор обработки. Сохранённый оригинал при ошибке метаданных восстанавливается сверкой. Изменение конфигурации парсера или индекса требует повторной обработки нужных версий с трассировкой, без перезаписи доказательств старых разборов.

## Добавление источника

1. Администратор или аналитик банка с разрешением на управление источниками выбирает поддерживаемый адаптер и вводит проверяемую конфигурацию.
2. Go проверяет схему, разрешённые сетевые адреса и перенаправления, ссылки на секреты, интервал опроса и административные права.
3. Создаётся источник; уровень доверия назначается по правилам реестра, интерфейс показывает начальное состояние.
4. Go создаёт отслеживаемую операцию синхронизации, которую выполняет Go-воркер; результат загрузки и последующая ML-обработка учитываются отдельно и видны в панели управления.
5. Для нового специализированного адаптера при реализации готовятся тесты на фиксированных примерах: успех, пустой или некорректный материал, превышение времени ожидания, лимит частоты, дубликат, изменение содержимого и небезопасный URL. Пока это план проверок.

Управление источниками показывает список и карточку, тип, доверие, включение, последнюю синхронизацию и успех, ошибки, возможности адаптера, настройку и состояние ручного запуска. Секреты и внутренние стеки ошибок не раскрываются. Срок хранения задаётся по классам данных: удаление оригинала не должно ломать происхождение утверждений старого разбора.
