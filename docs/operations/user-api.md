# Пользовательский API

## Реализованные маршруты

Все маршруты внешней `docs/api/openapi.yaml` подключены к Go. Данные сохраняются в PostgreSQL миграцией `000023_product_api.sql`.

| Маршрут | Назначение |
| --- | --- |
| `POST /v0.1/auth/login` | Локальный парольный вход, выдача session/CSRF cookie |
| `POST /v0.1/auth/logout` | Отзыв текущей сессии и удаление cookie |
| `GET /v0.1/me`, `GET /v0.1/contexts` | Пользователь и разрешённые контексты |
| `GET /v0.1/feed`, `GET /v0.1/alerts` | Снимок персонального ранжирования ML и предупреждения из него |
| `POST /v0.1/insights` | Постановка анализа в постоянную очередь; HTTP 202 |
| `GET /v0.1/generations/{id}` | Состояние операции и ссылка на сохранённый результат |
| `GET /v0.1/insights/{id}` | Сохранённая редакция разбора |
| `GET/POST /v0.1/insights/{id}/conversations` | Диалоги по конкретному разбору |
| `GET/POST /v0.1/conversations/{id}/messages` | История и асинхронный уточняющий вопрос |
| `POST /v0.1/insights/{id}/feedback` | Оценка конкретной редакции |
| `GET /v0.1/traces/{id}` | Безопасный статус обработки без промптов и внутренних журналов |
| `POST /v0.1/analytics/events` | Пакет клиентских событий с проверкой ссылок |
| `GET/POST /v0.1/admin/sources`, `GET/PATCH /v0.1/admin/sources/{id}` | Реестр источников |
| `POST /v0.1/admin/sources/{id}/syncs`, `GET /v0.1/admin/source-syncs/{id}` | Ручной опрос через существующий воркер |
| `GET /v0.1/admin/quality` | Фактические показатели опросов за период до 31 дня |

Служебные health/dataset endpoints сохраняются. Внутренние ML endpoints реализует ML-сервис, Go к ним обращается.

## Локальный вход

Корневой Compose включает локальный парольный вход. Сервер без Compose по умолчанию его отключает. Для HTTPS требуются `AUTH_COOKIE_SECURE=true` и точный `API_ALLOWED_ORIGINS`; значение `false` предназначено для локального HTTP. Секреты не передаются фронтенду и не возвращаются в JSON. Пароли хранятся как PBKDF2-SHA256 с отдельной случайной солью, 600000 итераций; токены сессии и CSRF — только как SHA-256.

Запуск из корня:

```sh
docker compose up -d --build
```

Создание пользователя выполняется оператором через `userctl`, публичной регистрации и назначения прав из браузера нет. Узнать доступные ключи компаний:

```sh
docker compose exec -T db psql -U burmalda -d burmalda -c 'SELECT synthetic_u FROM active_dataset_company_profiles LIMIT 10'
```

Создать пользователя для выбранного ключа. Пароль поступает на stdin; не передавайте его аргументом команды или через Git. Команда ниже читает пароль без отображения в терминале:

```sh
read -s API_PASSWORD
printf '%s\n' "$API_PASSWORD" | docker compose run --rm --no-deps -T api /app/userctl --login reviewer --name Reviewer --company-uid '<synthetic_u>' --role owner
unset API_PASSWORD
```

Команда возвращает `user_id` и `context_id`. При отсутствии активного профиля создаётся draft из исходных данных компании. Вход и список контекстов работают, аналитические запросы дают `409 PROFILE_NOT_READY`. Отсутствующий профиль не заменяется выдуманными признаками. `--company-id <UUID>` выбирает уже существующую компанию вместо импорта по ключу.

Подготовленный профиль можно передать через `--profile-file /path/in/container/profile.json` с bind mount. Файл содержит объект данных профиля; необязательный ключ `profile_features` — массив признаков ML v1, остальные поля передаются как `profile_data`. Для цитируемых признаков нужны настоящие `source_ref.source_snapshot_id`, `record_refs`, `derivation_version`; для группы — её подтверждённые contributing_company_ids. Числовой смысл спорных CSV-полей команда не назначает. Построение профиля ML остаётся отдельной интеграцией.

Для административного доступа оператор добавляет `--permissions sources:read,sources:manage,sources:trust`. Повторная установка пароля отзывает старые сессии пользователя. Новые полномочия явно задаёт оператор, а не пользовательский запрос.

Откройте [локальную страницу входа](http://localhost:18080/login), затем фронтенд на том же hostname (`localhost` или `127.0.0.1`) и обновите страницу. Cookie действуют между портами одного hostname; смешивать localhost и 127.0.0.1 нельзя. Origin страницы входа тоже должен быть в allowlist. В корневом Compose предусмотрены стандартные локальные адреса. Для production фронтенд и API удобно публиковать через один origin, как в nginx фронтенда: cookie CSRF нельзя прочитать с другого hostname.

Фронтенд может реализовать собственную форму: `POST /v0.1/auth/login` с `{login,password}`, JSON и `credentials: 'include'`. Для остальных POST нужно скопировать cookie `csrf_token` в `X-CSRF-Token`, также использовать `credentials: 'include'`. Вход не требует существующего CSRF-токена, но требует разрешённый Origin и проходит общие ограничения попыток в PostgreSQL. Logout принимает `{}`.

## Подключение ML

API получает из окружения:

- `ML_BASE_URL`, `ML_SERVICE_TOKEN` — адрес и служебный токен;
- `ML_ANALYSIS_CONFIG_VERSION` — подтверждённая ML версия генерации. Без неё новые операции не создаются;
- `ML_PIPELINE_VERSION` — отдельная подтверждённая версия обработки документов, требуемая общей конфигурацией ML-подключения;
- `ML_READ_DATABASE_URL` — необязательное отдельное подключение только для чтения корпуса ML. Без него читается схема `ml` в основной PostgreSQL.

Граница генерации — HTTP `POST /internal/v0.1/analyses`, `POST /internal/v0.1/follow-ups`, `GET /internal/v0.1/analyses/{analysis_id}`. Идемпотентный ключ равен сохранённому `request_operation_id`. Принимаются синхронный AnalysisResponse v1 и асинхронная AnalysisOperation. Лента загружается через `POST /internal/v0.1/feed-rankings`; Go сохраняет полный ограниченный снимок выдачи (не более 5000 карточек и 8 МиБ), включая ML pagination, затем выдаёт страницы по своему подписанному курсору.

ML владеет миграциями и записью событий/чанков. Текущий read adapter Go читает только `ml.events`, `ml.event_documents`, `ml.document_version_catalog`, `ml.document_versions`, `ml.document_chunks`. Это отдельная зависимость интеграции: в HTTP-контракте пока нет чтения полного события и исторических чанков для Go. При отдельной БД используется `ML_READ_DATABASE_URL`; роль должна иметь только USAGE на схему и SELECT на эти пять таблиц. Доступ к записи ML таблиц Go не нужен. Добавление HTTP чтения позволит заменить этот адаптер без изменения пользовательского API.

В проверенном ML PR #21 (`d8d2071`) HTTP entrypoint обслуживает article-processings; analyses/follow-ups/feed-rankings ещё не опубликованы. До их реализации реальные генерация и ранжирование недоступны. Тестовый ML используется только в тестах; runtime не содержит заглушек, демонстрационных разборов и искусственного fallback ранжирования. Отсутствие схемы/доступа к корпусу или ML-сервиса возвращает явную ошибку.

## Выполнение и повторы

Фоновый обработчик пользовательских операций стартует вместе с `cmd/api`. В PostgreSQL сохраняются запрос, исходные профиль/событие, trace и ключ до обращения к ML. Несколько экземпляров API используют lease и `FOR UPDATE SKIP LOCKED`. После рестарта или потери POST-ответа отправляется прежний запрос с прежним ключом. После GET 404 повторяется исходный POST, не создаётся независимый запрос модели. ML обязан сохранять соответствие ключа операции до платного вызова.

HTTP запрос ограничен `ml.request_timeout`, вся операция — `ml.max_processing_duration` (по умолчанию 30 минут), опрос — `ml.status_poll_interval`. Лимит ML2 в 120 секунд относится к внутреннему этапу и не требует держать пользовательское HTTP соединение открытым. Временные ошибки повторяются с ограниченной задержкой и разбросом, учитывается Retry-After. Terminal FAILED не запускает модель заново.

Результат проходит JSON Schema и проверки идентификаторов, точных цитат, происхождения банковских утверждений, ссылок на признаки и оговорок для partial support. Публичный результат и SUCCEEDED фиксируются одной транзакцией. Исходный ML ответ сохраняется отдельно. Старые чанки, источники и профиль в уточнении не заменяются текущими. В одном диалоге выполняется не более одного незавершённого уточнения; параллельный новый вопрос получает 409, повтор прежнего ключа возвращает прежнюю операцию. Размер вопроса — до 16000 UTF-8 байт, снимка запроса — до `ml.max_response_bytes`, история не обрезается незаметно.

Доступ проверяется при каждом чтении, включая generation, trace и историю. Владение чужим ID не предоставляет доступ. Cursor ленты связан с сессией, пользователем, контекстом, профилем, фильтром, размером страницы и сохранённым снимком. Снимки ленты живут час; старые курсоры дают 400. Завершённые ручные sync сохраняют состояние даже после retention истории source_polls.

Общие ограничения запросов на час: 30 попыток нового анализа/уточнения, 120 построений снимка ленты, 600 пакетов аналитики, 120 созданий диалога и 600 оценок; вход — 30 попыток по IP и 15 по логину. Счётчики хранятся в PostgreSQL. Пакет аналитики — 1–100 событий. Истёкшие счётчики и снимки удаляются небольшими пачками фоновым обработчиком.

## Проверка

```sh
cd backend
go test -race ./...
go vet ./...
TEST_DATABASE_URL='<отдельная тестовая PostgreSQL с правом CREATE DATABASE>' go test -race ./internal/userapi
```

Интеграционные тесты создают и удаляют собственные БД. Проверяются весь пользовательский сценарий, повторные ключи, изоляция ресурсов и отзыв прав, cookie/CSRF/logout, смена URL без sources:trust и ручной sync через планировщик с сохранением результата после очистки опросов. ML в этих тестах — локальный HTTP double по настоящим схемам; успешный тест не означает проверку реальных моделей.
