# Подключение сохранённого корпуса к ML

Go использует существующий `/internal/v0.1/article-processings`. Новые поля HTTP-запроса и отдельная quality-only операция не добавляются. `SUCCEEDED` по-прежнему означает завершение всего пайплайна; `event_ids: []` допустим. Окончательный `FAILED`, включая `error.retryable=true`, автоматически не создаёт новую операцию.

## Лимит и включение обработки

`ML_MAX_TEXT_BYTES` по умолчанию равен 131072. Можно задать меньший положительный предел; значение больше подтверждённого ML лимита отклоняется при запуске. Считаются байты UTF-8 `article.body`, без заголовка. Текст не обрезается. Ограничение проверяется при загрузке, постановке сохранённых версий и перед POST. Уже принятую операцию можно продолжать опрашивать через GET без повторной передачи текста.

Лимит действует и без `ML_PIPELINE_VERSION`. Пока ML не объявил поддерживаемое значение версии, эта переменная остаётся пустой: Go сохраняет материалы, но не создаёт задания. Адрес и токен ML задаются через `ML_BASE_URL` и `ML_SERVICE_TOKEN`.

## Постановка существующих версий

Из каталога `backend`, с настроенным `DATABASE_URL`:

```sh
go run ./cmd/mlctl enqueue --pipeline-version "$ML_PIPELINE_VERSION" --dry-run --limit 1000
go run ./cmd/mlctl enqueue --pipeline-version "$ML_PIPELINE_VERSION" --limit 1000
```

Команда требует непустую версию пайплайна. По умолчанию выбирается только последняя версия каждой статьи. Фильтры: `--source-id UUID`, `--article-version-id UUID`; `--all-versions` включает историю. Для следующей пачки передайте последний `next_after` как `--after UUID`; если `selected` меньше `limit`, обход завершён. UUID задаёт порядок обхода, а не дату публикации. При параллельном поступлении новых версий можно повторить обход: уникальность задания предотвращает дубли.

Операция читает сохранённые версии и оригиналы, не скачивает источник и не создаёт версий. В ответе для каждой версии указан результат: `QUEUED`, `WOULD_QUEUE`, `EXISTING`, `PAYLOAD_TOO_LARGE` или `SOURCE_SNAPSHOT_UNVERIFIED`. `dry-run` не меняет БД. Превышение лимита показывается в отчёте и не создаёт задание. Существующие задания, в том числе `FAILED`, не сбрасываются. Другая версия пайплайна создаёт отдельное задание с отдельным ключом.

В Compose команда доступна в образе:

```sh
docker compose run --rm --no-deps api /app/mlctl enqueue --pipeline-version "$ML_PIPELINE_VERSION" --dry-run
```

## Снимок источника и старые задания

Новые версии сохраняют безопасные поля источника и идентификаторы публикации в `article_version_source_snapshots`, даже когда ML ещё отключён. При последующей постановке используются эти поля; для старых версий можно переиспользовать снимок из ранее созданного подтверждённого задания. Только если обоих снимков нет, берётся текущая конфигурация с меткой `CAPTURED_AT_ENQUEUE`. `processing_jobs.source_snapshot_origin` различает:

- `CAPTURED_AT_INGEST`: сведения сохранены вместе с версией;
- `CAPTURED_AT_ENQUEUE`: исторического снимка нет, использована текущая конфигурация при подготовке задания;
- `UNVERIFIED_LEGACY`: миграция 000009 восстановила версию конфигурации для старого задания без доказанного исторического соответствия.

Миграция 000017 отмечает задания, созданные не позже применения 000009, как `UNVERIFIED_LEGACY`. Незавершённые задания получают диагностический код `SOURCE_SNAPSHOT_UNVERIFIED`. Воркер их не забирает; ключ, принятый `processing_id`, статус и сохранённые параметры не переписываются. Завершённые результаты сохраняются.

```sh
go run ./cmd/mlctl audit-legacy
```

Отчёт содержит общее число и до 1000 записей; `truncated=true` явно показывает неполную выборку. Перед разблокировкой необходимо восстановить исходный запрос по журналу/сохранённой ML-операции. Отсутствие доказательств нельзя заменять текущими настройками источника и повторять изменённый POST с прежним ключом. Команда не подтверждает такие задания автоматически. При обновлении окружения с подобными заданиями старые воркеры нужно остановить до миграции: старая сборка не знает о новом ограничении.

## Происхождение текста

В `article_versions` сохраняются `text_origin`, `extraction_method`, `extraction_issues`:

- `rss_summary`: текст взят из RSS/Atom; полнота публикации не подтверждена, даже если лента содержит `content:encoded`;
- `full_article`: текст извлечён из загруженной HTML-страницы;
- `pdf_extracted`: текст получен из PDF, включая OCR; `extraction_method` отличает OCR от обычного извлечения;
- `unknown`: для старой версии способ нельзя достоверно восстановить.

`full_article` не гарантирует сохранность таблиц, изображений и всех блоков. Пустой список `extraction_issues` означает отсутствие известных ошибок. Неуспешное извлечение диагностируется существующими ошибками опросов и заданий загрузки; оно не создаёт пригодную версию. Поля происхождения пока не включаются в POST: их имена и расположение должен согласовать ML. Выгрузка помещает их в сопроводительный manifest.

## Выгрузка payload для ML

```sh
go run ./cmd/mlctl export --output ./ml-payloads --limit 20
```

Каталог должен быть новым, его родитель должен существовать. Можно ограничить выборку через `--source-id` или `--article-version-id`. Экспорт берёт реальные версии из БД и использует тот же `RequestPayload`, что и HTTP-клиент. В каталоге находятся JSON-запросы и `manifest.json` с ключом идемпотентности, размером текста, происхождением и SHA-256 оригинала. Параметры доступа источника и сервисный токен не экспортируются. Файлы доступны только владельцу.

Если версия пайплайна ещё не задана, в примере стоит `UNCONFIRMED-FIXTURE-ONLY`, а manifest содержит `fixture_only=true`. Это пример для проверки формы и качества текста; отправлять его в рабочий ML нельзя. Задания не создаются, POST не выполняется. С явным `--pipeline-version` используется это значение и, при наличии задания, его исходные поля и trace ID. Сомнительный исторический снимок и превышение размера отражаются в manifest без файла POST.

Повтор той же версии проверяется повторной доставкой одного файла с тем же ключом из manifest. Пустой успешный список событий не является отказом качества.

## Проверки

`go test ./...` проверяет сериализацию, обязательные поля ответа, ошибки и границы размера, включая кириллицу и emoji. С `TEST_DATABASE_URL` дополнительно запускаются проверки очереди и БД: параллельная постановка, новая версия пайплайна, исходный снимок, потеря ответа, GET 404 с восстановлением прежнего POST, окончательный отказ, таймаут RUNNING, миграция старых заданий и экспорт без секретов. ML-тесты создают и удаляют отдельные временные схемы. HTTP ML в этих тестах подменяется управляемым транспортом; это не подтверждает работу настоящего ML-сервиса.

## Extraction metadata и категории источников

Новые задания сохраняют `delivery_extraction` в транзакции постановки в очередь. Поле `text_origin` отображается в `article.metadata.extraction_method`; технический парсер (`provided-text` и другие) остаётся внутренним. Известные коды извлечения передаются без потери, дубли удаляются. Диагностика `PAGE_COUNT_MISMATCH: TXT contains N pages; PDF contains M` при N < M становится `MISSING_PAGES`. Остальные неизвестные проблемы и `text_origin=unknown` останавливают отправку с `INVALID_ML_REQUEST`; исправлять их догадками нельзя.

Миграция 000020 заполняет снимок только для QUEUED-заданий без попыток и без принятой операции. Уже отправленные старые задания сохраняют прежний payload, включая metadata; их нельзя незаметно переводить на новый контракт с тем же ключом. Для восстановления неизвестного происхождения проверяют оригинал и путь обработки, затем создают отдельно согласованную операцию переобработки. Экспорт показывает некорректные материалы как `INVALID_ML_REQUEST` без файла запроса.

Реестр принимает source_type: `news`, `bank_analytics`, `expert`, `regulator`, `financial_press`; trust_level: `primary`, `trusted`, `standard`, `unknown`, `reviewed`. Значения передаются без автоматического повышения доверия. Новый payload с неподдерживаемой категорией сохранённого снимка не отправляется. Проверить существующий реестр можно запросом:

```sql
SELECT id, source_type, trust_level FROM sources
WHERE source_type NOT IN ('news','bank_analytics','expert','regulator','financial_press')
   OR trust_level NOT IN ('primary','trusted','standard','unknown','reviewed');
```

При `SUCCEEDED` Go проверяет равенство `document_version_id = article_version_id`. Иное значение в ответе POST или GET — `INVALID_ML_RESPONSE`: задание завершается ошибкой, результаты не записываются. Для каждой пары `(article_version_id, pipeline_version)` остаётся отдельное задание; ML обязан сохранять результаты разных пайплайнов раздельно и не перезаписывать старые чанки и доказательства.
