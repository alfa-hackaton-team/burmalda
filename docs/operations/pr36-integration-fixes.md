# Исправления интеграции PR #36

База: `e5f7b8fd7353918f9d43cc2ca8e01d928248b5f5`. Рабочая ветка:
`fix/pr36-integration`. Это отдельный checkout; исходная ветка
`feature/precomputed-insights` и работающий пользовательский стенд не изменены.

## Поведение

- ID результата и новых claims назначает ML runtime детерминированно по
  `request_operation_id`. Ссылки citations на новые claims переназначаются вместе
  с ними; ссылки на исходные claims не изменяются. Неоднозначные повторные labels
  отклоняются. Тексты, evidence, числа, атрибуция и verifier не изменены.
- Конфликт уникальности при сохранении результата завершает Go-операцию с
  `INVALID_ML_RESPONSE`, без повторов сохранения до таймаута.
- Открытие события находит операцию того же пользователя с теми же доверенными
  снимками контекста, профиля, роли, события и версии конфигурации. Приоритет:
  активная операция, успешная, безопасный отказ. Новый browser key привязывается
  к найденной операции в PostgreSQL. Тот же ключ с другими параметрами даёт 409.
- Только явное действие `force_new=true` с новым ключом создаёт повторный анализ.
  Frontend предлагает его после окончательного отказа, а не после локального
  таймаута ожидания выполняющейся операции. Обычное открытие и reload не требуют
  этого признака. Уже сохранённый успешный разбор не скрывается неудачной новой
  попыткой.
- Для внешнего события добавлен отдельный semantic-поиск по готовым последним
  версиям материалов зарегистрированного источника банковского импорта
  `uuid5(NAMESPACE_URL, 'alfa-hackathon-reference-pdfs')`, роль `bank`, доверие
  `primary`. Дополнительные IDs определяет сервер. Произвольные bank/external
  источники не допускаются. Известные даты банковских публикаций не могут быть
  позже даты события. Доказательства события не заменяются банковским контекстом.
  Follow-up использует только исходный сохранённый снимок, без нового поиска.
- `canonical_url` сохраняется в источниках ленты. Ссылка из раздела evidence ведёт
  через Go к конкретной версии документа, фактически использованной в Insight.
- Ошибки проверки показываются безопасными русскими сообщениями и trace ID;
  сырой ответ модели не выводится. Решения денежно-кредитной политики отнесены к
  financing.

## Дополнения HTTP

Существующие DTO и формы успешного анализа не изменены. В OpenAPI описаны:

- необязательный `force_new: boolean` в `POST /v0.1/insights`, по умолчанию false;
- `GET /v0.1/insights/{insight_id}/documents/{document_version_id}/original`:
  сессия, владелец и текущий context grant обязательны; версия должна присутствовать
  в сохранённых chunks. Публичный HTTP(S) URL открывается через 307. Закрытый файл
  выдаётся attachment после проверки SHA-256 и размера, максимум 32 MiB. Внутренний
  S3 URI и ключи клиенту не возвращаются. Ответы не кешируются.

Go API получает уже существующую S3-конфигурацию из Compose. Новый API-процесс
только читает оригиналы, не создаёт bucket и не загружает документы.

## Применение

1. Объединить миграции с PR #35 **до** применения к общей базе. В PR #35
   зарезервированы Go `000024_precomputed_insights.sql`,
   `000025_insight_grounding_diagnostics.sql` и ML
   `000002_follow_up_operations.sql`. В этой ветке используются Go
   `000026_recent_news.sql`, `000027_insight_operation_aliases.sql` и ML
   `000003_product_api.sql`. Применить общий набор существующими командами
   миграций **до** обновления сервисов; содержимое SQL не изменено.

   База, уже запущенная с прежними именами `000024_recent_news.sql`,
   `000025_insight_operation_aliases.sql` или `000002_product_api.sql`, требует
   отдельного перехода с проверкой журналов и схемы. Простая замена файлов
   несовместима с такими журналами. Не удалять записи о миграциях и не выполнять
   SQL повторно. Go также не применяет добавленные миграции с номером ниже уже
   применённого: сначала объединить наборы, затем применять их по порядку.
2. Собрать Go, Python и frontend из этой ветки. Обновлять backend/Python перед
   frontend: новый интерфейс использует добавленный маршрут оригиналов. Для новых результатов использовать
   новую согласованную `ML_ANALYSIS_CONFIG_VERSION` одновременно в Go и Python,
   например `ml-analysis-v2`; это отделит старые результаты от новой конфигурации
   контекста. Если старую версию оставить, прежние результаты могут быть
   восстановлены вместо нового вычисления.
3. Использовать существующий ML overlay/profile и кэш закреплённых весов по
   [инструкции запуска](../ml/docker.md). Эти исправления не скачивают веса и
   не включают ML автоматически.
4. Проверить gateway в целевом окружении до live smoke. В локальной DNS-проверке
   26 октября оба адреса — `changellenge.up.railway.app` и
   `api.alfahack-gateway26.ru` — разрешались. Это не проверка авторизации,
   доступности моделей или лимитов. Активный gateway и пользовательский `.env`
   автоматически не менялись. Резервный адрес применять только в согласованном
   окружении.

## Границы проверки

Детерминированные проверки и PostgreSQL-тесты используют изолированные временные
БД; production-модели и рабочие сервисы при них не вызываются. Перед сдачей нужен
малый live-прогон собранной интеграции: успешный анализ с ручной проверкой всех
claims/citations, корректный insufficient_evidence, follow-up и повторное открытие
без новой ML-операции. Статистическую стабильность эти исправления не доказывают.

Банковский поиск расширен только на общий импортированный набор. Это не новая
универсальная ACL-система для любых частных документов. Релевантность найденной
аналитики и выводов требует обязательной существующей верификации. Поля дат,
если отсутствуют в исходном документе, автоматически не восстанавливаются.

## Результаты проверок этого изменения

- После разделения номеров общий набор SQL из PR #35 и этой ветки проверен
  на отдельных пустых PostgreSQL-базах: Go применил 27 миграций, ML2 — 3;
  повторный запуск обоих миграторов не применил ничего. Полные Go-тесты и
  89 ML runtime-тестов прошли на новых тестовых базах.
- `go test -race -count=1 -p 1 ./...`: PASS, 16 пакетов с тестами,
  PostgreSQL, одноразовые базы; `go vet ./...`: PASS.
- `python -m unittest discover -s ml_runtime/tests -q`: **89/89 PASS**,
  включая PostgreSQL и проверки доверенного банковского scope. Без пропусков.
- Frontend `npm run check`: форматирование, **32/32 PASS**, TypeScript и Vite
  production build.
- Генерация контрактов `--check`, 16 ML fixtures, 261 локальная ссылка API,
  публичные fixtures и фактические Go payload-примеры: PASS.
- ML1 real-weight suite, новые платные анализы и перезапуск рабочего стенда
  не выполнялись. Semantic-релевантность банковского поиска на настоящей модели
  и браузерная интеграция с работающим Go/S3 требуют отдельного live-подтверждения.

Тесты подтверждают: неверные UUID модели заменяются служебными до verifier;
ссылки claims/citations сохраняются; коллизия ID завершает операцию;
reload/store recreation возвращают прежнюю операцию без новых ML-вызовов;
ключ остаётся связан с fingerprint; новый профиль не получает прежнюю операцию;
закрытый оригинал нельзя получить по чужому Insight, посторонней версии или
после отзыва grant; повреждённый оригинал не выдаётся. Follow-up не открывает
корпус и не получает дополнительную банковскую аналитику.
