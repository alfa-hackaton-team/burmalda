# Контракты API v0.1

Статус: DRAFT. TEAM DECISION D11: два OpenAPI 3.1 с общими схемами. Пути, идентификаторы, значения перечислений, постраничная выдача и соответствие ошибок HTTP-кодам — ASSUMPTION D16; они предложены для согласования контрактов и имитаций API на стороне интерфейса. Наличие YAML не означает, что все поля одобрены и API готов к эксплуатации.

- [openapi.yaml](openapi.yaml): интерфейс ↔ серверная часть; бизнес-контекст, лента, предупреждения, разборы, диалоги, обратная связь, безопасная трассировка, аналитика и административные операции.
- [ml-openapi.yaml](ml-openapi.yaml): серверная часть ↔ ML-сервис; профили, поиск и ранжирование, генерация и уточняющие ответы, реестр источников, синхронизация и наблюдаемость.
- [schemas.yaml](schemas.yaml): общие структуры `BusinessContext`, `ProfileRef`, `Evidence`, `Claim`, `AgentResponse` и вспомогательные форматы обмена (DTO). Относительные `$ref` задают единое определение, без копирования структур.

## Почему две спецификации

Внешний API описывает пользовательские ресурсы, внутренний — доверенные запросы к ML и границу работы с инструментами. Интерфейс не передаёт роль, пользователя или версию профиля как доверенные входные данные: сервер определяет их и формирует `TrustedRequestContext`. Общие схемы позволяют ML1 вернуть пакет доказательств `EvidencePackage`, ML2 — ответ `AgentResponse`, а серверу — разбор `Insight`, сохраняя смысл утверждений. Внутренние операции не должны быть доступны извне вместе с публичным API.

## Что намеренно не выбрано

Q01: не заданы `securityScheme`, операции входа и управления сессиями, а также способ передачи авторизации. Это открытое условие реализации, а не разрешение анонимного доступа. Все клиентские, административные и внутренние операции требуют проверки доверенного контекста; права на группу и разделение административной и клиентской зон согласуются отдельно. Имитация API не доказывает безопасность.

Q07: немедленный ответ `200` и ответ о принятии в обработку `202` — альтернативы проекта. Они не означают выбор гибридного варианта без измерений и согласования. Предлагаемые операции получения состояния `Generation` отмечены; интерфейс может имитировать оба варианта для оценки пользовательского сценария. До реализации необходимо выбрать вариант, при принятии зафиксировать RFC/ADR, удалить невыбранные ветви и согласовать ответ, `Location`, повторы и получение результата.

Q14: строковый идентификатор со скрытой внутренней структурой не определяет тип первичного ключа SQL; соответствие идентификаторов и версий рассматривается вместе со схемой БД. `ProfileRef(version)` и `document_version_id` обязательны для восстановления происхождения выводов; конкретный формат версий остаётся проектным предложением.

## Обязательные свойства контрактов

1. Выбор ровно одного объекта — компании или группы — моделируется `oneOf`; поле `kind` различает контексты. Сам идентификатор контекста не даёт право доступа.
2. Все существенные публичные утверждения `Claim` связаны с доказательствами в `AgentResponse.evidence`. Ссылки на материалы и признаки содержат версии; произвольные URL источников без происхождения данных не заменяют подтверждение.
3. Тип утверждения и результат проверки различаются. `UNSUPPORTED` доступен для внутренней проверки, но не публикуется как подтверждённый факт. Для `PARTIALLY_SUPPORTED` нужны оговорки или ограничения; подтверждение прогноза означает подтверждение его оснований.
4. `Section.claim_ids` указывают на существующие утверждения; удалённое утверждение не остаётся в разделе. Для `ALFA_ANALYTICS` нужны материалы банка; выводы модели обозначаются отдельно.
5. `Insight` фиксирует событие, контекст, роль и профиль. Диалог `Conversation` наследует их; тело сообщения не может менять исходные границы анализа. Сообщения упорядочены, история сохраняется между сессиями; параллельные запросы требуют отдельного согласования.
6. `AgentResponse` и `Insight` не содержат секретов или скрытых рассуждений модели. Публичная трассировка возвращает только разрешённые сведения после проверки прав.
7. `Idempotency-Key` предложен для платных операций и создания ресурсов; до реализации согласуются границы действия, срок хранения и поведение при повторе. Ключ не разрешает кэширование финальных персональных ответов между пользователями.
8. Для коллекций используется постраничная выдача по курсору. В ленте курсор связан с зафиксированными ранжированием, профилем и конфигурацией; изменение контекста или фильтра требует нового прохода. Устойчивый порядок при равных оценках и срок действия курсора согласуются при реализации.
9. Конфигурация источника `SourceConfig` ограничена разрешёнными адаптерами, проверкой схемы, безопасными адресами и перенаправлениями, ссылками на секреты. Поле `adapter_config` не обходит проверки сети и учётных данных.
10. Ошибки единообразны; отсутствие подтверждений отличается от недоступности ML. Безопасный ограниченный разбор может быть успешным результатом; невозможность подтвердить выводы — `INSUFFICIENT_EVIDENCE`. Соответствие HTTP-кодам и правила повторов согласуются до утверждения контракта.

## Передача контрактов между интерфейсом, сервером и ML

Разработчик интерфейса может готовить имитации по схемам: успешная и пустая лента, неготовый профиль, полный или ограниченный разбор, ожидание и ошибка генерации, уточняющий ответ, сбой источника и отсутствие метрик качества. Эти тестовые данные не обещают реализацию всех предложенных операций. Серверный разработчик и ML3 совместно согласуют HTTP-контракт, ошибки и порядок выполнения; ML1/ML2 проверяют `EvidencePackage`, `AgentResponse` и правила утверждений. Интеграционные тесты должны проверять преобразование данных, внешние ссылки, изоляцию контекстов, повторы запросов и согласованность версий.

Полностью синтетические примеры: [лента](examples/feed.json), [разбор с ограничениями](examples/insight-limited.json), [пакет доказательств](examples/evidence-package.json). Это иллюстрации DTO, не ответы работающей модели и не реальные новости или данные банка. `requires-review` в примере — тестовая метка, а не выбранная продуктовая шкала.

## Требования к проверке контрактов

Перед утверждением контрактов проверять OpenAPI 3.1 и JSON Schema, разрешение `$ref`, уникальность `operationId`, обязательные параметры путей и соответствие тестовых данных схемам. В CI выбранного стека добавить проверки преобразования данных, изоляции контекстов, идемпотентности и согласованности версий. Проверка структуры DTO не заменяет проверку авторизации и поведения работающих сервисов.
