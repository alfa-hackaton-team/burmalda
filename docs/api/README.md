# Контракты API v0.1

API связывает пользовательский интерфейс, серверную часть и ML-сервис. Контракт описывает не только структуру JSON, но и смысл операции: какой контекст используется, какие права проверяются, как получить результат и что происходит при ошибке.

- [openapi.yaml](openapi.yaml) — внешний API: пользователь, контексты, лента, предупреждения, разборы, диалоги, обратная связь, безопасная трассировка, продуктовая аналитика и административные функции.
- [ml-openapi.yaml](ml-openapi.yaml) — внутренний API: профили, поиск, ранжирование, генерация, уточнения, обработка материалов от Go и показатели ML. Управление источниками и синхронизацией принадлежит Go и описано во внешнем API.
- [schemas.yaml](schemas.yaml) — общие форматы `BusinessContext`, `ProfileRef`, `Evidence`, `Claim`, `AgentResponse` и вспомогательные структуры. Относительные `$ref` связывают обе спецификации с одним определением.

## Почему две спецификации

Пользовательский API работает с доступными человеку ресурсами. Внутренний API получает доверенный контекст и выполняет аналитическую обработку. Интерфейс не назначает роль, пользователя или версию профиля: сервер определяет их, проверяет доступ и формирует `TrustedRequestContext`.

ML1 возвращает `EvidencePackage`, ML2 — `AgentResponse`, сервер формирует ресурс `Insight`. Общие схемы сохраняют смысл утверждений и доказательств на каждой границе. Внутренние операции не выставляются наружу вместе с клиентскими.

## Контекст доступа и получение результата

Внешний API использует серверную сессию в cookie `session_id` с `HttpOnly`, `Secure` и `SameSite`. Go получает `user_id` только из проверенной сессии и в БД проверяет доступ к компании или группе и выбранной роли. Для административных операций нужны отдельные полномочия. На изменяющих запросах обязательны `X-CSRF-Token`, связанный с сессией, и проверка разрешённого `Origin`. Механизм входа выдаёт сессию и CSRF-токен; продуктовый API описывает их использование, а не отдельную интеграцию с банковским входом.

Внутренний API использует `Authorization: Bearer <SERVICE_TOKEN>`. Это служебный секрет, не JWT, из окружения или хранилища секретов. ML проверяет его на каждом запросе, принимает контекст только от аутентифицированного Go и валидирует согласованность данных. Интерфейс не вызывает ML; ML доступен только через внутреннюю сеть и защищённое соединение. Секреты не хранятся в Git, логах и ответах. В OpenAPI заданы `securitySchemes`, `security` и ответы `401`/`403`.

Создание разбора и отправка уточнения описывают две формы доставки. При синхронном выполнении HTTP 200 содержит готовый результат. При асинхронном HTTP 202 содержит операцию, по которой можно получить состояние и ссылку на сохранённый результат. Операция не становится успешной до появления доступного пользователю ресурса. Практические условия применения режимов описаны в [разборе генерации](../rfc/0002-insight-generation-lifecycle.md).

Идентификаторы API скрывают внутреннюю структуру хранения. Они не обязаны быть SQL UUID и не совпадают автоматически с исходными синтетическими ключами. `ProfileRef` и `document_version_id` фиксируют конкретные версии, чтобы обновление данных не меняло основания прежнего ответа.

## Обязательные свойства контрактов

1. **Ровно один объект анализа.** `BusinessContext` использует `oneOf` для компании или группы. Поле `kind` различает тип. Идентификатор контекста не является правом доступа.
2. **Адресуемые основания.** Существенные утверждения `Claim` ссылаются на `AgentResponse.evidence`; материалы и признаки содержат версии. Произвольный URL без происхождения не заменяет доказательство.
3. **Разделение смысла и проверки.** Тип утверждения не равен результату проверки. `UNSUPPORTED` используется внутри, но не публикуется как факт. `PARTIALLY_SUPPORTED` требует оговорки. Подтверждение прогноза относится к основаниям, не гарантирует будущее.
4. **Целостность разделов.** `Section.claim_ids` указывают на существующие утверждения; удалённое утверждение не остаётся в разделе. `ALFA_ANALYTICS` опирается на материал банка, а вывод модели обозначается отдельно.
5. **Фиксированный диалог.** `Conversation` наследует разбор, контекст и роль. Тело сообщения не подменяет их. Сохраняется упорядоченная история; параллельные ответы не должны терять связь с вопросами.
6. **Безопасное представление.** Ответы не содержат секретов и скрытых рассуждений модели. Внешняя трассировка показывает только разрешённые сведения.
7. **Контролируемые повторы.** `Idempotency-Key` обязателен для `POST /v0.1/insights` и `POST /v0.1/conversations/{conversation_id}/messages`. Go транзакционно сохраняет ключ и отпечаток клиентских параметров до запуска ML. Тот же ключ и параметры возвращают прежнюю операцию или результат; другие параметры с тем же ключом дают `409`. Уникальность пользователя, типа операции и ключа защищает от параллельного запуска. При повторе доступ проверяется заново, но профиль и конфигурация исходной операции не пересчитываются.
8. **Устойчивая постраничная выдача.** Курсор связан с конкретной выдачей, профилем и конфигурацией. Смена контекста или фильтра начинает новый проход. При одинаковых оценках порядок остаётся устойчивым.
9. **Проверяемая конфигурация источника.** Разрешены поддерживаемые адаптеры, безопасные сетевые адреса и ссылки на секреты. `adapter_config` проходит схему конкретного адаптера и не обходит проверку сети.
10. **Различимые ошибки.** Отсутствие доказательств отличается от недоступности модели. Безопасный ограниченный ответ может быть полезным результатом; невозможность подтвердить выводы возвращается как `INSUFFICIENT_EVIDENCE`.

При уточнении Go однократно сохраняет пользовательское сообщение и фиксирует границу истории, передаваемой ML; повтор не добавляет второе сообщение и не меняет исходный запрос к модели.

Go передаёт стабильный идентификатор сохранённой операции как обязательный внутренний `Idempotency-Key` для анализа и уточнения. ML сохраняет связь с выполнением до платного вызова и устраняет повторные запросы Go. Таймаут без известного результата провайдера не приводит к слепому повтору платного вызова: сохраняется состояние, проверяется результат либо возвращается контролируемая ошибка. Ключи активных операций не удаляются; срок хранения завершённых покрывает окно повторов. Это защита повторов операции, а не межпользовательский кэш ответов.

## Передача контрактов между интерфейсом, сервером и ML

Интерфейсные имитации используют те же структуры, что и реальный сервер: успешная и пустая лента, неготовый профиль, ожидание, полный или ограниченный разбор, ошибка, уточняющий ответ, сбой источника и отсутствие метрик. Это позволяет проверять поведение экранов до подключения всей цепочки.

Сервер и ML проверяют сериализацию, ссылки на внешние схемы, изоляцию контекстов, повторы и версии. Для аналитического ответа важно не только наличие массива доказательств: ссылки утверждений должны разрешаться, тип доказательства — соответствовать смыслу, а ограничения — доходить до интерфейса.

Синтетические примеры: [лента](examples/feed.json), [разбор с ограничениями](examples/insight-limited.json), [пакет доказательств](examples/evidence-package.json). Они иллюстрируют DTO, а не результаты работающей модели и не реальные данные банка. Тестовая метка `requires-review` в примере относится к демонстрационной шкале влияния.

## Требования к проверке контрактов

Проверки охватывают OpenAPI 3.1, JSON Schema, разрешение `$ref`, уникальность `operationId`, обязательные параметры путей и соответствие примеров схемам. Семантические проверки дополнительно оценивают принадлежность ресурсов контексту, целостность версий и идемпотентность.

В CI интеграционные сценарии проверяют совместное поведение компонентов. Структурно правильный JSON не доказывает корректность авторизации, правдивость вывода или успешное сохранение результата — эти свойства проверяются отдельно.
