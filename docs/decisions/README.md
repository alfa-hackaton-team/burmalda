# Обоснование архитектуры

Описание архитектуры должно объяснять не только устройство системы, но и причины её границ. Например, отдельные API защищают внутренние ML-операции, сохранённые версии поддерживают проверяемость выводов, а раздельная подготовка ленты и подробного разбора контролирует стоимость.

## Что фиксируется

Для значимого изменения сохраняются задача, ограничения, описание подхода, рассмотренные альтернативы, измерения, последствия и связанные документы. Важно указать, какое свойство улучшается и какой ценой: дополнительные ресурсы, задержки, усложнение восстановления или новые зависимости.

Числа сопровождаются методикой: набором данных, конфигурацией, размером выборки и условиями запуска. Ссылка на измерение полезнее общего заявления о производительности или масштабируемости.

## Связь документов

Продуктовые последствия отражаются в PRD, границы компонентов — в архитектуре, смысл сущностей — в модели, форматы обмена — в OpenAPI. Изменение хранения или генерации не должно оставлять противоречащие описания в разных документах.

[Принципы и параметры системы](../planning/decision-register.md) дают общий обзор. [Архитектурные разборы](../rfc/README.md) раскрывают темы с существенными компромиссами. Описание не требуется для каждой мелкой правки поля; его цель — сохранить понятное обоснование там, где оно помогает разработке и сопровождению.
