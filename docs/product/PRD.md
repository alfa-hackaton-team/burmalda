# PRD: персонализированная новостная аналитика

Версия 0.1, 2026-10-22. Status: DRAFT. Основания и статусы: [реестр](../planning/decision-register.md); покрытие PDF: [матрица](../planning/case-compliance.md). Это product truth после review; здесь нет физической схемы и спецификации endpoints.

## Проблема и ценность

CASE REQUIREMENT C01–C06. Руководитель компании с выручкой более 15 млрд ₽ уже имеет доступ к новостям. Ему нужно понять, какие события существенны для его бизнеса, через какие механизмы они создают риски/возможности и как их оценивает Альфа-Банк. Отраслевой пересказ без связи с конкретными признаками клиента не решает задачу.

Ценностный результат: пользователь получает проверяемое объяснение «что изменилось → почему это важно моему бизнесу → возможные последствия и сценарии → что говорит банк → на каких данных это основано». Сервис помогает принять решение; действия из аналитики не исполняются автоматически.

## Пользователи и jobs

| Пользователь | Job | Ожидаемый угол анализа |
|---|---|---|
| CEO / собственник | Выделить стратегически значимые изменения и зависимости группы | Рынок, операционные зависимости, долгосрочные сценарии |
| CFO | Оценить влияние на финансирование и финансовую устойчивость | Заёмные продукты, стоимость финансирования, оборотный капитал |
| Казначейство / главный бухгалтер / другие ЛПР | Уточнить последствия в своём разрезе | Ликвидность, платежи и релевантные функции роли |
| Bank Admin / Bank Analyst | Управлять источниками и контролировать качество | Source health, evidence, feedback, ошибки и расход моделей |

CASE REQUIREMENT: аудитория включает перечисленные роли. ASSUMPTION: конкретные role-specific акценты выше — гипотезы для экспертной проверки, не знание о фактических обязанностях тестового пользователя. TEAM DECISION: demo роли моделируются синтетически; роль берётся из доверенного backend context. Выбор поддерживаемых demo roles согласовать при подготовке fixtures; CEO/CFO — предложенный минимум для сравнения.

## Scope v0.1

TEAM DECISION D02–D09: Company и Group, сохранённый CompanyProfile, роль, персональная лента событий, high-impact state, on-demand анализ, диалог внутри Insight, источники, trace, feedback, Source Management и Quality UI. Person links и payments включены как источники контекста ML1; полезность конкретных graph features должна быть подтверждена EDA.

CASE REQUIREMENT: интерактивный сквозной прототип, поддерживающий новые материалы, неполные данные и собственный агентный процесс.

FUTURE: Story engine, behavioral recommender, webhook sources, увеличение analytics storage при измеренной потребности. Не входят: произвольная регистрация компании, глобальный blank chat, arbitrary-web crawler, автоматическое выполнение финансовых действий, обязательная реальная интеграция с банковским IAM. Имитация банковского shell и аккаунтов должна быть явно указана в THIRD_PARTY_NOTICES/README финальной сдачи.

## Основные сценарии

1. Пользователь открывает постоянно доступную точку входа в shell Альфа-Бизнеса.
2. Backend определяет доверенную identity/role и доступные business contexts. Правила доступа Q01 пока TBD; UI не предлагает неавторизованные контексты и не назначает роль произвольной строкой.
3. Пользователь выбирает Company либо Group. Для группы видно, какой scope анализируется; вклад компаний в вывод можно раскрыть.
4. Лента показывает event previews, объяснение «почему вам», источники, дату/тему и понятный impact state. Переключение контекста меняет выдачу, а не только заголовок.
5. Открытие карточки запускает full analysis. До готовности пользователь видит честное состояние; sync/async transport TBD Q07, но UX обязан различать ожидание, результат, недостаток evidence и ошибку.
6. В Insight различимы событие, связь с бизнесом, риски, возможности, сценарии/действия, аналитика банка, AI-выводы и источники каждого существенного утверждения.
7. Пользователь уточняет вопрос в этом Insight. Агент сохраняет контекст и при необходимости расширяет evidence. История доступна после новой сессии; правила доступа к ней остаются предметом Q01.
8. Пользователь открывает основание вывода, допустимую часть trace и оставляет feedback.

Дополнительный сценарий: Bank Analyst открывает Source Management, добавляет конфигурацию поддержанного adapter, проверяет status, запускает sync и наблюдает восстановление после ошибки. Создание неподдержанного источника не обещает автоматическую поддержку.

## Functional requirements и приёмка

| ID | Requirement / status | Acceptance |
|---|---|---|
| FR01 | Контексты Company/Group, доверенная роль — TEAM DECISION | Один Event даёт различающийся обоснованный разбор для разных ролей и scopes; доступ ограничен backend |
| FR02 | Сохранённый профиль — TEAM DECISION | Видны дата/версия использованного профиля и missing features; rebuild не меняет основания старого Insight |
| FR03 | Сбор внешних и банковских материалов — CASE REQUIREMENT | Новый материал проходит загрузку → обработку → выдачу; один упавший source не блокирует остальные |
| FR04 | Ранжирование событий — CASE REQUIREMENT | На одном corpus разные business contexts дают осмысленно разные top results; дубль публикации не занимает отдельную карточку того же Event |
| FR05 | Объяснение релевантности — CASE REQUIREMENT | Preview указывает реальные признаки профиля и механизм связи; нет выдуманного долга/экспорта/контрагента |
| FR06 | Полный анализ по открытию — TEAM DECISION | Feed не требует full generation каждого элемента; повторный запрос не создаёт бесконтрольные платные дубли |
| FR07 | Содержательная интерпретация — CASE REQUIREMENT | Доступны риски/возможности/сценарии, либо явное объяснение, почему данных недостаточно; не требуется выдумывать позитивную возможность для каждого события |
| FR08 | Банк отдельно от AI — CASE REQUIREMENT | Нет bank evidence → честно «подходящая позиция не найдена», а не сгенерированная позиция банка; конфликт источников явно отмечен |
| FR09 | Claim-level grounding — TEAM DECISION, реализует C06 | Каждый существенный опубликованный claim содержит проверяемые references; inference отмечает допущения, UNSUPPORTED не выдаётся как факт |
| FR10 | Follow-up — CASE REQUIREMENT / TEAM scope | Уточнение использует тот же Insight/context/role; нехватка evidence приводит к retrieval или честному ограничению; несвязанный вопрос не превращает чат в глобальный |
| FR11 | High-impact alerts — TEAM DECISION | Alert привязан к Event/context и обоснованию; threshold Q11; не требует заранее полного Insight; scope и роль согласованы с feed |
| FR12 | Feedback — TEAM DECISION | 👍/👎 привязаны к версии Insight; отрицательный feedback допускает причину/комментарий; UI показывает результат отправки |
| FR13 | Source Management — TEAM DECISION | Список, конфигурация, enable/disable, sync и health; secrets не возвращаются в UI |
| FR14 | Quality UI — TEAM DECISION | Видны usage, source health, ошибки, latency, feedback, model/token usage; offline ranking quality имеет дату/выборку/версию, не выдумывается из CTR |
| FR15 | Trace — CASE REQUIREMENT | По доступному trace можно восстановить sources/features/tools/verification; hidden reasoning не показывается |

## Состояния и ограничения продукта

ASSUMPTION: названия состояний UI уточняются при дизайне экранов; их семантика обязательна для покрываемых сценариев.

- Нет доступных contexts: сообщение и путь к ответственному за demo accounts; не регистрация новой компании.
- Profile отсутствует/строится/устарел: отличить от пустой ленты; явно обозначить актуальность.
- Нет релевантных событий: честный empty state, не случайные популярные новости.
- Источник degraded: сохранённый материал остаётся доступен с датой, ошибки не удаляют corpus.
- Evidence недостаточно или противоречиво: ограниченный разбор с явными пробелами вместо ложной уверенности.
- Модель недоступна, timeout или бюджет исчерпан: сохранённые previews/готовые разрешённые материалы остаются доступны; повтор анализа контролируется.
- Контекст или роль изменились: не показывать старую персональную интерпретацию как новую; диалог остаётся привязанным к исходному Insight.
- Disclaimer появляется в релевантном финансовом/инвестиционном контексте; текст Q13 TBD, не механически на каждой карточке.

## Измерение успеха

CASE REQUIREMENT: качество, мониторинг и обратная связь. TEAM DECISION: сравнивать retrieval/ranking и grounding объективно.

Primary ML metric пока TBD: NDCG@K/Recall@K/MRR по экспертной разметке. Primary product signal — полезность персональной аналитики по feedback и экспертной рубрике, а не число запросов. Guardrails: unsupported assertions, source/Alfa coverage, ошибки, p95 latency, стоимость и alert false positives. Значения K, выбор primary metric и пороги фиксируются после eval setup; сейчас числа не выдумываются.

Приёмка дизайна: сценарии и контракты согласованы, TBD видны, mocks можно строить по DRAFT schemas. Приёмка продукта: измерения реально проведены, E2E работает, auth/lifecycle gates закрыты. Подробности — [demo/evaluation](../demo/demo-evaluation.md).
