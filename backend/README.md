# Go-бэкенд

Один Go-модуль содержит процессы `api`, `worker`, мигратор и локальную команду `sourcectl`. API предоставляет проверки состояния, а воркер опрашивает RSS/Atom-источники и сохраняет версии материалов в PostgreSQL. Внешний административный API будет подключён после реализации серверной авторизации.

## Локальный запуск

Требуется Go 1.25+ и Docker Compose. Из каталога `backend`:

```sh
docker compose up -d db
cp config.example.yaml config.yaml
export BACKEND_CONFIG_FILE=./config.yaml
export DATABASE_URL='postgres://burmalda:burmalda@127.0.0.1:5432/burmalda?sslmode=disable'
go run ./cmd/migrate
export HTTP_ADDR=127.0.0.1:18080
go run ./cmd/api
```

В другом терминале из того же каталога:

```sh
export BACKEND_CONFIG_FILE=./config.yaml
export DATABASE_URL='postgres://burmalda:burmalda@127.0.0.1:5432/burmalda?sslmode=disable'
go run ./cmd/worker
```

## Рабочие настройки

В [config.example.yaml](config.example.yaml) перечислены лимиты и таймауты API, загрузки источников и ML-воркера. `BACKEND_CONFIG_FILE` задаёт путь к YAML; без него используются прежние значения по умолчанию и переменные окружения. Неуказанные поля YAML получают значения по умолчанию. Неизвестное поле или некорректное значение останавливает запуск. После правки файла отправьте работающему процессу `SIGHUP`: новый набор параметров применяется целиком к следующим операциям. При ошибке перечитывания процесс продолжает работать с прежним набором и пишет ошибку в лог.

Новые опросы источников получают обновлённые лимиты, сетевые таймауты и настройки планировщика; уже начатый опрос завершается со старым набором. Новые запросы и задания ML используют обновлённые параметры. Таймаут проверки готовности API меняется без перезапуска. `database.*` и `server.read_header_timeout` применяются при запуске и требуют перезапуска. `DATABASE_URL`, `HTTP_ADDR`, `ML_BASE_URL`, `ML_SERVICE_TOKEN`, `ML_PIPELINE_VERSION` и `ML_MAX_TEXT_BYTES` остаются переменными окружения; их изменение тоже требует перезапуска. Интервал конкретного источника хранится в реестре и меняется через `sourcectl patch`.

Проверки API: `curl http://127.0.0.1:18080/health/live` отвечает без обращения к БД, а `/health/ready` проверяет PostgreSQL и возвращает `503`, когда соединение недоступно. Оба процесса завершаются по `SIGINT`/`SIGTERM`. Остановить локальную БД: `docker compose down` (данные останутся в volume).

## Миграции

SQL-файлы лежат в [migrations](migrations). Команда `go run ./cmd/migrate` применяет новые версии по порядку в одной транзакции, берёт advisory lock и записывает контрольные суммы в `schema_migrations`. Повторный запуск безопасен; изменение уже применённого SQL останавливает команду с ошибкой. Миграции запускаются отдельно перед запуском новой версии сервисов. Автоматического отката нет: для изменения схемы добавляется следующий SQL-файл.

Первая миграция создаёт `sources`, `source_polls`, `raw_artifacts`, `articles`, `article_versions` и `processing_jobs`. Оригинал HTML/PDF хранится в `raw_artifacts.content` (`bytea`) либо по `object_uri`; ровно одно место хранения обязательно. Для одинаковых байтов одного источника используется один артефакт по SHA-256. `article_versions` остаются отдельными версиями нормализованного текста и ссылаются на артефакт. Сроки хранения и партиционирование пока не заданы: сначала нужно утвердить retention и зависимости доказательств от версий.

Миграция `000003` добавляет к версии статьи необязательные язык и автора, объект метаданных и проверку непустого текста. Задание на ML хранит безопасные поля источника отдельными колонками, чтобы повторить исходный запрос после изменения реестра. `source_id` берётся из версии статьи. Для пары `(article_version_id, pipeline_version)` уже действует уникальность; успешное задание обязано содержать `document_version_id`. Численный предел текста и состав `metadata` ещё согласуются с ML1.

Миграция `000004` разрешает новую версию статьи при возвращении ранее встречавшегося текста. Дубликат проверяется относительно текущей версии статьи, а не всей её истории.

## Реестр источников

`sourcectl` — локальная команда оператора, работающая напрямую с PostgreSQL. Её можно использовать до подключения сессионной авторизации административного API. Команды из каталога `backend` при установленном `DATABASE_URL`:

```sh
go run ./cmd/sourcectl create source.json
go run ./cmd/sourcectl list 25
go run ./cmd/sourcectl get SOURCE_ID
go run ./cmd/sourcectl patch SOURCE_ID CONFIG_VERSION patch.json
```

`source.json` соответствует `SourceConfigInput` в [схеме API](../docs/api/schemas.yaml). Например:

```json
{
  "name": "Example feed",
  "source_type": "news",
  "source_role": "external",
  "trust_level": "reviewed",
  "adapter_type": "rss",
  "endpoint": "https://example.com/feed.xml",
  "enabled": true,
  "polling_interval_seconds": 900
}
```

Проверенные стартовые конфигурации: [Federal Reserve](examples/sources/federal-reserve-press.json) и [ECB](examples/sources/ecb-press.json). На 24 октября 2026 года HTML-режим сохранил 20 полных пресс-релизов Federal Reserve и 15 материалов ECB, включая PDF. Конфигурации добавляются через `sourcectl create` по отдельности; обе используют интервал один час, поскольку HTML-режим заново загружает все ссылки ленты при каждом опросе.

Принимаются конфигурации `rss` и `atom` с пустым `adapter_config` либо `{"article_html": true}` и без `credential_ref`. Этот режим загружает материалы по ссылкам ленты: HTML-страницы с непустым `<article>` или `<main>`, а также текстовые PDF. Для иной разметки источника можно задать `article_container_id` и список `article_exclude_classes` в `adapter_config`, например `{"article_html":true,"article_container_id":"article","article_exclude_classes":["heading"]}`. Эти настройки относятся к записи источника, а не к домену в коде. Режим включают только для проверенных источников, чьи ссылки ведут на тот же host, что и лента. Интервал — от 60 секунд до суток. При сохранении проверяются URL и его текущие DNS-адреса; воркер повторит проверку при каждом сетевом соединении и перенаправлении. `patch` принимает частичный JSON и требует актуальный `config_version`; изменение конфигурации сбрасывает lease воркера, а смена адреса или адаптера также сбрасывает HTTP-валидаторы и курсор. Команда имеет доступ к БД и предназначена для доверенного оператора, не для вызова из интерфейса.

Маршруты `GET/POST /v0.1/admin/sources` и `GET/PATCH /v0.1/admin/sources/{source_id}` реализованы в `internal/sources.AdminHandler`. Они не подключены к `cmd/api`, пока нет серверной сессии, проверки административных прав, CSRF и Origin. Конструктор требует авторизатор; без него маршруты не создаются. При подключении PATCH использует `If-Match: "<config_version>"`, а ответы возвращают `ETag`.

## Планировщик опроса

Пакет `internal/polling` выбирает включённые источники по `next_poll_at` через `FOR UPDATE SKIP LOCKED`, выдаёт lease и создаёт `source_polls` со статусом `RUNNING` в одной короткой транзакции. Сетевой запрос выполняется после её завершения. Владелец может продлить lease и завершить опрос; устаревший владелец не может записать результат. Сохранение материалов выполняется через `Outcome.Persist` в той же транзакции, что и завершение опроса, после проверки lease. Просроченные или сброшенные при изменении источника попытки переходят в `FAILED`, после чего источник можно выбрать снова. `cmd/worker` запускает RSS/Atom-адаптер. `SOURCE_POLL_LEASE`, `SOURCE_POLL_IDLE` и `SOURCE_POLL_REAP_BATCH` задают его рабочий цикл.

Адаптер загружает ленту с ограничением 4 МиБ, проверяет DNS и адрес каждого соединения и перенаправления, использует `ETag`/`Last-Modified`, разбирает не более 500 записей за опрос. Исходный XML сохраняется в PostgreSQL как `raw_artifact`. В обычном режиме `article_version` ссылается на снимок ленты; текст берётся из `content:encoded`/Atom `content`, при отсутствии — из `description`/`summary`.

Для источника с `article_html=true` воркер заново читает ленту и до 20 ссылок на статьи за каждый опрос, даже если лента не менялась: опубликованная статья могла измениться отдельно. Ссылка и все перенаправления должны оставаться на host ленты; переход с HTTPS на HTTP запрещён. HTML и PDF ограничены 4 МиБ. Основной текст HTML извлекается из `<article>` либо `<main>` или из настроенного контейнера, без навигации, скриптов, подвала и указанных исключаемых классов. Из текстовых PDF до 100 страниц извлекается текст без OCR. PDF без извлекаемого текста получает явную ошибку записи. Версия ссылается на сохранённые байты страницы или PDF; XML ленты хранится отдельно. Изменение меню вне основного текста не создаёт версию. Источник с более чем 20 ссылками получает ошибку опроса; для него нужен отдельный адаптер или пересмотр лимита.

Ошибка отдельной статьи не отменяет остальные записи. Опрос с удачными и неудачными статьями получает статус `PARTIAL`, источник — `DEGRADED`, а URL и причина каждого сбоя сохраняются в `source_poll_entry_failures`. Если не удалось обработать ни одну статью, статус — `FAILED`. После частичного или полного сбоя HTTP-валидаторы ленты не продвигаются, чтобы проблемные записи попали в следующий опрос. При успешном повторе ранее сохранённые версии не дублируются.

Для ошибочной статьи с URL создаётся отдельное задание в `article_fetch_jobs`. Временные сетевые ошибки, HTTP 408/429/5xx повторяются независимо от опроса ленты: задержка растёт с разбросом и не бывает меньше `Retry-After`. После `article_retry.max_attempts` задание становится `DEAD`; постоянные ошибки переходят в `DEAD` сразу. Успешная загрузка этой статьи при очередном опросе ленты закрывает задание. Задания хранятся в PostgreSQL, выбираются через `SKIP LOCKED`, используют lease и восстанавливаются после его истечения. Параметры повторов задаются в `article_retry` файла `config.yaml`. Ошибка без URL остаётся только в истории опроса и требует исправления источника. Состояние источника снова станет `HEALTHY` после успешного полного опроса.

Когда заданы подтверждённая ML-командой `ML_PIPELINE_VERSION` и согласованный с ML1 `ML_MAX_TEXT_BYTES`, новая версия и `processing_job` записываются в одной транзакции. Лимит считается по размеру UTF-8 `article.body` в байтах, без заголовка; превышение отклоняется без обрезания. Задание хранит снимок значимых полей источника, включая `config_version`, поэтому повтор отправляет прежние значения после изменения реестра. При наличии `ML_BASE_URL` и `ML_SERVICE_TOKEN` второй цикл воркера отправляет сохранённый материал в ML через HTTP, восстанавливает потерянный ответ с тем же `Idempotency-Key`, опрашивает состояние, ограниченно повторяет временные ошибки и сохраняет `document_version_id` с `event_ids` после успеха. Неподдерживаемую версию, неверный материал, конфликт ключа и слишком большой запрос автоматически не повторяет. Пока ML не объявил лимит и поддерживаемую версию, оставьте обе переменные пустыми: новые версии будут загружаться без ML-заданий. Для их последующей обработки понадобится отдельная переобработка.

Миграция `000009` заполняет `source_config_version` у ранее созданных заданий текущей версией источника: прежняя версия в БД не сохранялась. Если конфигурация источника после создания задания менялась, такие задания перед отправкой в ML нужно проверить или создать повторно с точным снимком.

Проверка двух конкурирующих воркеров и восстановления после истечения lease запускается на отдельной тестовой БД: `TEST_DATABASE_URL=postgres://... go test ./internal/polling -run TestTwoWorkersClaimOneSource -v`. Без `TEST_DATABASE_URL` интеграционный тест пропускается.

Параметры окружения перечислены в [.env.example](.env.example). `DATABASE_URL` обязателен; остальные имеют значения по умолчанию. Примерные учётные данные предназначены только для локальной разработки. Не сохраняйте рабочие секреты в репозитории.

## Наблюдаемость

Из каталога `backend` запустите локальный стек:

```sh
docker compose -f compose.yaml -f compose.observability.yaml up -d --build
```

[Grafana](http://127.0.0.1:13000/d/ingestion-overview) открывается по адресу `http://127.0.0.1:13000`; локальный просмотр доступен без входа, учётные данные администратора по умолчанию — `admin` / `admin`. Задайте `GRAFANA_ADMIN_PASSWORD` перед запуском, если адрес будет доступен другим пользователям. Дашборд «Источники и обработка» появляется автоматически. [Prometheus](http://127.0.0.1:19092) доступен на порту 19092.

Compose запускает PostgreSQL, мигратор, один воркер, отдельный сборщик состояния БД, Prometheus, Loki, Tempo, Alloy и Grafana. Дополнительные экземпляры воркера запускаются через `docker compose -f compose.yaml -f compose.observability.yaml up -d --scale worker=2`; Prometheus обнаруживает их через DNS сервиса.

Воркер отдаёт метрики по `/metrics`, когда задан `METRICS_ADDR`. В Compose это `:19090`; сборщик состояния БД отдаёт агрегаты на `:19091`. Имена прикладных метрик начинаются с `ingestion_`, а `service.name` в логах и трейсах — `ingestion-worker` или `ingestion-observer`. Счётчики попыток принадлежат отдельному процессу воркера, а очереди и актуальность источников вычисляются из PostgreSQL один раз в сборщике. JSON-логи остаются в stdout и одновременно отправляются через Alloy в Loki. Трейсы отправляются в Tempo по OTLP/HTTP, когда задан `OTEL_EXPORTER_OTLP_ENDPOINT`.

На дашборде сверху показаны устаревшие источники, размер очереди, `DEAD` и задержка обработки; ниже — результаты опросов, длительность, ответы `429/503`, таблица проблемных источников и логи. Ссылку на конкретный трейс можно найти по `trace_id` в логе или в `source_polls.trace_id`, затем открыть Explore → Tempo. Правила оповещений видны в Grafana Alerting: недоступность воркера или сборщика, устаревшие источники, `DEAD`, отставание очередей и повторяющиеся ошибки. Канал доставки уведомлений нужно настроить в Grafana для своего окружения. В локальном Compose Grafana подключается к PostgreSQL с демонстрационными учётными данными; на сервере для этого подключения нужен отдельный пользователь с правом только `SELECT`.

Исходники дашборда и правил находятся в [observability/grafana](observability/grafana). После изменения генераторов пересоздайте JSON командой `python3 observability/grafana/generate_dashboard.py && python3 observability/grafana/generate_alerts.py` и перезапустите Grafana. Остановить стек: `docker compose -f compose.yaml -f compose.observability.yaml down`; данные мониторинга остаются в Docker volumes.
